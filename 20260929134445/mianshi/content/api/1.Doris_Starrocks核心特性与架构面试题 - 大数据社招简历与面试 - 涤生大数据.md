### 存算分离架构和存算一体架构该如何选择？（艾特尔信息）
在选择 Doris/StarRocks 的存算一体或存算分离架构时，可从业务需求、资源弹性、部署复杂度三个维度决策：
（1）存算一体架构
特点：计算与存储在同一节点，部署简单，无外部存储依赖，数据本地性强，查询性能极致。
适用场景：业务数据规模稳定、对弹性扩缩容要求低，追求极致查询性能的场景（如企业内部核心报表分析、数据量增长平缓的业务）。
（2）存算分离架构
特点：计算与存储解耦，存储依赖共享存储（如 S3、OSS），计算资源可弹性伸缩，云原生适配性强。
适用场景：数据量爆发式增长、需动态调整计算资源（如互联网用户行为分析、流量波动大的业务），或追求存储与计算独立扩缩的云原生场景。
简言之，若业务追求性能稳定、部署简单，选存算一体；若业务需弹性扩缩、适配云原生，选存算分离。

### Doris/Starrocks的FE节点的选举机制
FE 节点分为 follower 和 observer 两类。各个 FE 之间，通过 bdbje 进行 leader 选举，数据同步等工作。Doris 将 FE 元数据存储在嵌入式的 BDBJE 数据库中，并通过其
高可用复制机制（HA Replication） 实现多节点一致性和主节点选举。
初始化复制组
启动时，每个 Follower FE 进程会尝试加入指定的复制组（通过配置中的 priority_networks, edit_log_port, rpc_port 等字段标识自己）。
所有 Follower 会自动发现并连接其他 FE 节点，组成一个 BDBJE 的 Replication Group。
选举规则（基于 Paxos算法）
BDBJE 使用类 Paxos 算法来从所有 Follower 节点中选出一个 Master（observer不参与选举）。
拥有多数节点可用（即 >N/2 个节点存活）时才可进行选举。

### Doris/StarRocks的分布式事务是如何实现的？
StarRocks实现分布式事务的机制主要基于以下几个方面：

### 两阶段提交：采用两阶段提交协议来保证分布式事务的一致性。在第一阶段，事务协调器询问所有参与节点是否可以提交事务；如果所有节点都同意，那么在第二阶段进
行实际的提交操作。

### 事务日志： 每个事务操作都会记录在事务日志中，这些日志用于在发生故障时恢复事务状态，保证事务的持久性和一致性。

### 版本控制：使用多版本并发控制（MVCC）来管理数据版本，这样可以支持在读取数据时不锁定数据，优化并发性能。

### 故障恢复： 在发生节点故障时，能够通过事务日志和保存的状态信息来恢复未完成的事务，确保数据一致性不受影响。

### 分布式共识协议： 使用分布式共识协议(Raft)协议保证分布式系统中数据的一致性。只有大多数副本写入成功，事务才会被认为是提交成功的

（1）多版本并发控制(MVCC):

### Doris/Starrocks 如何的FE/BE是如何保证数据一致性的？（飞轮科技）
FE数据一致性：FE 采用类 Raft 协议（BDB JE 协议）（Doris/StarRocks 均用）保证元数据强一致，只有 Leader 可写，变更同步到多数 Follower 才提交，确保所有 FE 元
数据完全一致。导入/更新/删除以事务为单位，要么全部成功可见，要么全部失败回滚，无中间状态。
BE数据一致性：每个数据分片有多个副本，BE 之间通过 Raft 日志同步 + Quorum 多数派写入，确保至少半数副本写入成功才返回成功，保证副本数据完全一致。BE 写
入采用 WAL 预写日志 + 批量提交，数据先写日志再落盘，机器宕机重启后可恢复，保证单节点写入不丢、不乱。
FE 定期检查 BE 副本状态、数据版本、分片完整性，发现副本缺失 / 版本不一致时，自动发起副本补齐、版本同步，保证全局数据一致。

### 介绍一下BE的半数写入机制（飞轮科技）
BE 的半数写入机制，就是多副本写入时必须满足多数派（>1/2）成功才算成功，既保证数据强一致、不丢失，又提升写入性能和可用性，是 Doris/StarRocks 高可靠的核
心机制。比如一个 Tablet 数据默认 3 副本，写入时必须保证 至少 2 个副本成功（> 半数）。只要满足 多数派成功，就向 FE 返回事务成功，剩下不足的副本，后台异步补
齐，不影响写入延迟。

### 介绍一下Doris/Starrocks里面的version？（飞轮科技）
在 Doris 和 StarRocks 里，Version 就是数据的版本号，由 FE 统一分配、全局单调递增，每次导入或更新事务提交都会生成一个新版本。
它主要用来实现 MVCC 多版本并发控制，保证读写互不阻塞、查询能拿到一致的快照数据，不会读到未提交或中间状态的数据。同一主键的多条数据会靠 Version 区分新
旧，Version 更大的就是最新数据，在 Unique 表和主键表做数据合并、去重覆盖时，就是以 Version 作为判断依据。同时 Version 也用于分布式事务和多副本一致性，只
有所有副本都同步到对应版本，数据才对外可见，从而保证整个集群的数据一致。后台 Compaction 也是按 Version 来合并小文件、清理旧版本，既减少文件数量提升查询
性能，又能回收存储空间。

（1）整体架构：MPP架构 + 向量化执行：Doris 和 StarRocks 都是典型的 MPP（Massively Parallel Processing）架构，查询时会把 SQL 拆分成多个并行的 fragment，
在各个 BE 节点上并发执行。
（2）存储层：列式存储 + 数据裁剪
Doris 和 StarRocks 的存储层都是基于 列式存储，同类数据连续存放，天然利于向量化计算。
性能核心点在于：
列裁剪：查询只读取需要的列，其他列完全不扫描。
谓词下推（Predicate Pushdown）：过滤条件直接在存储层生效，能尽量减少 IO。
前缀/Zone Map / Bloom Filter / MinMax 等索引：存储文件中带有列值范围（Min/Max），快速跳过不相关数据块。
（3）执行层：向量化执行引擎
Doris / StarRocks 的查询执行是向量化的，也就是一次处理一批数据，不像传统火山模型那样一行一行处理。
优势：
CPU Cache 命中率高（批量操作避免频繁函数调用）；
SIMD 指令并行加速（利用 CPU 指令集同时处理多条数据）；
减少函数调用栈消耗；
算子计算优化（多个算子批量执行）。
（4）Pipeline 执行模型
新版本的 Doris和 StarRocks都引入了 Pipeline 执行模型，这是一个巨大的性能提升点。

### ClickHouse 的 Join 性能为什么比starrocks/doris 差？（阿里巴巴/飞轮科技）
ClickHouse 的 Join 性能相对较差，主要是由于其架构设计和功能特性的局限性。以下是 ClickHouse 在 Join 性能方面的劣势，以及 Doris/starrocks 的优势对比：
架构设计限制 ：
ClickHouse 采用两层汇聚的执行框架，缺乏完善的 MPP 查询层，对复杂查询的支持较差，在大表之间的 Shuffle Join 场景下表现不佳
相比之下，Doris/starrocks 基于 MPP 架构，拥有完善的执行框架和向量化执行引擎，能够支持复杂的 SQL 分析，包括大小表的 Broadcast Join 和大表之间的
Shuffle Join
Join 类型支持有限 ：
ClickHouse 仅支持 Global Join（对应Broadcast Join）和 Local Join（对应Colocation Join），在大表 Join 大表时，需要将右表广播到所有节点，性能受限
Doris/starrocks 支持四种 Join 方式，包括 BroadCast Join、Shuffle Join/Bucket Shuffle Join 和 Colocation Join，能够根据数据规模和查询类型选择最优的 Join 策
略
优化器和索引不足 ：
ClickHouse 缺乏基于成本的优化器（CBO），无法对 Join 操作进行有效的优化。其聚合能力采用 Scatter Gather 模式的 2 阶段聚合，第二阶段为单节点，对内存和
CPU 的消耗较大
Doris/starrocks 拥有较完善的 CBO，能够根据数据分布和查询计划选择最优的执行方式。其聚合能力采用多节点并行聚合计算，结合 Runtime Filter 技术，进一步提
高 Join 性能
内存和数据处理能力 ：
ClickHouse 的 Join 默认倾向于使用 Hash Join，要求右表能够完全加载到内存中构建哈希表。当右表过大时，会尝试将数据溢写到磁盘，导致性能显著下降
Doris/starrocks 在设计上考虑了更复杂的 OLAP 场景，通过分区分桶裁剪、点查索引（主键、倒排）等技术，进一步提高并发度和 Join 性能

### Doris/Starrocks是如何实现高性能的多维分析？
Doris（StarRocks 架构逻辑类似）主要通过以下技术手段实现高性能多维分析：
列式存储优化：采用列式存储，多维分析时仅读取查询所需列，大幅减少 IO 开销，提升查询效率。
高效索引支持：提供 Bitmap、Bloom Filter、倒排索引等动态索引，快速定位数据，缩小扫描范围，加速多维度过滤查询。
预聚合（物化视图）：通过物化视图实现预聚合，数据导入时提前计算并存储聚合结果，查询时直接复用预计算结果，减少实时计算量，显著提升多维度聚合查询速
度。
复杂查询优化机制：内置谓词下推、列剪裁、Join 优化等机制，例如谓词下推可提前过滤数据，降低后续计算的数据集规模，提升多维关联查询性能。
灵活数据模型适配：支持明细、聚合、更新等多种数据模型，可根据多维分析场景（如明细探查、多维度聚合）灵活选择，保障查询效率。
分布式 MPP 架构：采用 MPP 的分布式架构，支持水平扩展，查询任务在多个节点并行执行，满足海量数据下的多维分析性能需求。

### Doris/Starrocks 与 Clickhouse有什么区别？（必看，极其高频面试题）
Doris、StarRocks 和 ClickHouse 都是主流的 MPP 架构 OLAP 引擎，核心区别主要体现在架构设计、SQL 能力、查询性能、数据更新、易用性和适用场景上：
ClickHouse 是单一节点性能极强的列存引擎，单表查询、写入吞吐、数据压缩非常不错，适合日志、监控、时序这类大宽表场景，但多表关联能力弱、SQL 兼容性一般、
运维和扩缩容比较复杂，也不擅长频繁实时更新。
Doris/Starrocks 架构非常简单，而且完全兼容 MySQL 协议和语法，开箱即用、运维简单、支持在线扩缩容，同时提供明细、聚合、Unique 多种数据模型，实时更新和多
表 Join 能力明显优于 ClickHouse，而且并发能力很强，综合性能均衡，非常适合实时数仓、BI 分析、数据中台，日志等场景。

### Doris/Starrocks 有哪些机制来保证数据的高可用？（卓繁信息）
主要通过以下机制保障数据高可用：
数据分片与多副本：将数据划分为多个分片（tablet），每个分片存储多个副本（replica，建表时候指定副本数）并分布在不同物理节点。即使单个节点故障，系统可
从其他节点的副本读取数据，保障数据可访问性。
元数据冗余存储：元数据在多个节点间冗余存储，避免元数据单点故障，保障元数据的高可用与一致性。
多种数据恢复机制：支持备份/跨集群数据同步等方式，可在实际生产故障后，通过备份恢复数据，降低业务中断风险。

### Doris/Starrocks和Hive对比说说有啥区别？（中科软/中数智汇/科大讯飞/恒创嘉越/吉贝克-海尔外包 ）
Hive 是构建在 Hadoop 之上的离线数仓引擎，采用存算分离架构，数据存储在hdfs或者s3上，依赖 MapReduce 或 Spark 执行计算，查询延迟高，以批量 ETL、数据清洗
和离线统计为主，事务与实时更新能力较弱。
Doris 是MPP 架构的实时分析数仓，存算一体、自带分布式存储（Doris3.0之后支持存算分离，数据可以存储在hdfs或者s3上，主要是为了节省成本），采用向量化执行引
擎，查询延迟低、并发能力强，支持实时写入与 Upsert 更新，更适合交互式分析和高并发报表服务。
延伸的话，也可以和spark对比下（科大讯飞问过）

### doris是什么特性能让你们在项目中把ADS层放到doris，解决你们实际业务什么问题（南京365网络）
把 ADS 层放到 Doris，主要利用它低延迟查询、高并发、MySQL 兼容、实时写入更新的特性。既能支撑高并发报表、大屏、自助分析等毫秒级响应需求，又能直接对接实
时数据做到T+0 实时指标，同时运维简单、稳定性强。解决了传统方案查询慢、并发低、实时性差、组件繁多难维护的问题，实现了统一的 ADS 查询服务。

### doris/starrocks缺点有哪些？（携程/杭州消金）
整体在实时分析场景表现优异，但仍存在短板。在存算一体架构下，存储与计算绑定，弹性扩缩容不灵活，容易出现资源浪费，且大查询、高并发场景下易出现内存压力
大、OOM 等问题。引入存算分离后，虽然解决了弹性与存储成本问题，但会带来性能损耗，查询延迟和吞吐不如存算一体稳定，对网络和共享存储依赖极高，架构也更复
杂、运维难度更大。同时，Doris/Starrocks 对复杂嵌套类型、半结构化数据支持较弱，不擅长长时批处理与重度 ETL，多表大关联仍需谨慎设计，周边生态工具链相比
Hive 等传统组件也不够完善，多租户隔离能力相对有限。

### 介绍Doris为啥比Spark快（花茎教育）
Doris 采用 MPP 全内存并行 + 向量化执行引擎，查询无需落盘（4.0版本之后支持落盘，可选），而 Spark 基于批处理，中间结果频繁读写磁盘，IO 开销极大。同时 Doris
支持智能索引、前缀过滤、Runtime Filter 等优化，大幅减少数据扫描与网络 Shuffle，整体延迟比 Spark 低一个数量级，在多维分析与多表关联场景下速度优势尤为明显。

### starrocks和Doris对比（畅唐网络/Aftership/枫叶互动）
一、Apache Doris 与 StarRocks 详细系统对比

### 起源与 License
Doris：源自百度 Palo，Apache 顶级项目，Apache 2.0 协议，完全开源、无商用限制。
StarRocks：基于早期 Doris 分支自研，Linux 基金会，早期 Elastic 协议，现转为 Apache 2.0，但企业版高级功能闭源。

### 核心架构（几乎同源）
均为 FE（元数据）+ BE（计算存储） 、MPP + 向量化执行引擎、RAFT 高可用、分区 + 分桶分布式存储。
都支持存算分离和存算一体的架构
3. 功能差异
（1）数据模型与更新能力
Doris：支持 Unique / Aggregate / Duplicate 三种模型；支持灵活列更新、高并发写入、Group Commit、时序 Compaction，高频导入性能更稳定。
StarRocks：比Doris多一个 Primary Key 模型，支持行更新与部分列更新；无灵活列更新，不支持时序 Compaction。
（2）半结构化与多模态支持
Doris：原生支持 Variant 类型、JSON、倒排索引、IK/ICU/ 自定义分词；支持向量检索与10+ LLM 内置函数（分类、抽取等）。
StarRocks：半结构化能力和分词能力有限，无 LLM 函数，向量检索能力弱。
（3）存储与冷热分层
Doris：支持列存、行列混存、部分列行存；支持 HDD + SSD + 对象存储三级冷热分层。
StarRocks：支持列存、行列混存；不支持部分列行存，冷热分层两级分层（HDD/SSD）。
（4）数据湖与湖仓一体
Doris：支持 10+ 外部数据源，Iceberg 增量读取、Time Travel、Branch/Tag 能力完善。
StarRocks：仅支持少量数据源，缺少增量读取、数据回溯等核心能力。
（5）高可用、容灾与运维
Doris：支持跨集群复制（CCR）、磁盘间副本均衡、IO 隔离、大查询自动限流。
StarRocks：不支持跨集群复制、不支持磁盘间均衡、不支持 IO 隔离，资源管控能力弱。
