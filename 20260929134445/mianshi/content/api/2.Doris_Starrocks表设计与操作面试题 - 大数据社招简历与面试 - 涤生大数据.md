### Doris/StarRocks 的分区和分桶有什么区别，怎么去选择？（必看，极其高频面试题）
分区是更高层级的逻辑划分，分桶是分区内部的物理存储划分（即分桶是分区内的细分）。分桶会将分区后的每段数据打散
为逻辑分片Tablet。
划分依据：
分区：基于业务逻辑字段（如时间、地域）。
分桶：基于高基数字段（如用户 ID）+ 哈希算法。
核心作用：
分区：快速定位数据区间，减少全局数据扫描量。
分桶：让数据在分区内均匀分散，提升并行查询效率。
选择与结合策略
选分区表：数据量大，需频繁按时间、地域等字段快速过滤数据（如实时时序数据查询）。
选分桶表：数据含高基数字段，需并行处理多维度查询（如用户行为的并发分析）。
注意：单个 Tablet（分桶）（Tablet 数 = 分区数 * 桶数 * 副本数）的数据量理论上没有上下界，除小表（百兆维表）外需确
保在 1G - 10G 的范围内：
如果单个 Tablet 数据量过小，则数据的聚合效果不佳，且元数据管理压力大。
如果数据量过大，则不利于副本的迁移、补齐，且会增加 Schema Change 或者 物化 操作失败重试的代价（这些操
作失败重试的粒度是 Tablet）。

### Doris/StarRocks 的分区策略及其优化方式是什么？（悦智）
StarRocks 的分区策略是将数据根据特定的列（分区键）值分散存储到不同的分区中。这样做可以优化查询性能，原理和方
法如下：

### 分区键选择： 选择合适的分区键是优化查询性能的关键。通常选择经常用作查询条件的列作为分区键，可以有效减少查
询时需要扫描的数据量。

### 分区范围： 根据业务需求合理设定分区范围，如按照时间范围（如日、月、年）或其他业务逻辑划分，以确保数据分布
均匀，避免某些分区过大而影响查询性能。

### 分区方式：可以手动分区，也支持动态/自动分区功能，可以自动创建和删除分区，简化分区管理，并保证数据分布的实
时性和均衡性。

### 分区裁剪： 在执行查询时，会根据查询条件对分区进行裁剪，只扫描包含相关数据的分区，减少数据扫描量，加速查询
响应。

### Doris/Starrocks 里面的列存是如何设计的？相对行存来说，有什么区别？
（1）Doris / StarRocks 列存设计要点
列式物理布局：同一列的值连续存放，按列分 page/segment 写入与读取，便于只读所需列，减少 I/O。数据以
page 为最小编码/压缩单元，多个 page 组成 segment/文件，文件尾存元数据和索引，读取按需加载。
编码与压缩：列级采用多种编码（plain, delta, dictionary 等）和压缩，提高压缩比与 CPU 解压效率（同类型数据压
缩更好）。
多种内置索引：ZoneMap（min/max）、短键/前缀索引（Short-Key/Prefix）、Ordinal、以及可选的 Bitmap /
BloomFilter 等，用来快速跳过大量无关 page/file，减少扫描。
写入路径：MemTable→Flush→Segment：写到内存表后批量转为列式文件并生成索引（短键、zone map 等）；这
是列存高吞吐的关键。

（2）列存和行存关键区别
1. 访问模式
列存：适合宽表的分析型负载（聚合、扫描、少列选择）；读取少量列但大量行时优势巨大。
行存：适合点查/事务/单行写多（OLTP），单行所有列一次性读写开销低。

### I/O 与压缩
列存：同类型数据压缩率高，磁盘带宽利用率好；但读取 SELECT * 或很多列时会产生对每列的独立 I/O。
行存：压缩较差，但单行读写仅需一次 I/O（特别在小宽度表上更优）。

### CPU/执行模式
列存：向量化处理、谓词下推、早期投影（列裁剪），CPU 利用更高。
行存：逐行处理更简单，适合事务语义与复杂行内操作。

### 更新与写入延迟
列存：写入通常为批量（MemTable flush），随机写/频繁行级更新代价高（需写新version + 后台
compaction）。
行存：支持原地更新，延迟低（适合高并发写/更新）。

### 索引与跳过扫描
列存依赖 ZoneMap/short-key/bloom/bitmap 等索引来大幅减少扫描量（这是列存仍能做高效点查/过滤的手
段）。

### Bitmap 索引与Bloom filter 索引适用场景与限制（微创）
（1）Bitmap 索引：为每个取值构建一个 bit 位图（这一列第 N 行是否等于该值），多个位图可按 AND / OR 快速组合，适
合高效过滤与聚合。
适用场景：
低基数列（如性别、状态码， distinct 值≤1000），因位图存储效率随基数升高急剧下降；
精确等值查询（如where status=1）及逻辑组合查询（and/or），通过位图位运算快速计算结果。
限制：
高基数列不适用（如用户 ID），会导致位图数量激增，存储和维护成本过高；
不适合频繁更新场景（如实时写入），单条记录更新需修改多个位图，性能损耗大。
（2）Bloom Filter 索引：基于哈希函数构建位数组判断“值是否存在”，存在一定概率误判，但不会漏判。
适用场景：
高基数列（如订单号、URL），无需存储精确信息，仅需快速判断 “值是否可能存在”；
作为前置过滤（如where id=xxx），减少无效数据扫描，常用于查询的早期阶段。
限制：
存在假阳性（误判 “存在”），不能用于精确查询，需配合后续验证；
不支持范围查询（如>, <）和排序；
低基数列性价比低（低基数更适合 Bitmap），且哈希函数设计影响准确性。

### Doris/Starrocks 的表模型有哪些？分别适用于哪些场景？（必看，极其高频面试题）
Doris 有Duplicate/Aggregate/Unique三种模型，Starrocks 比它多一个Primary Key，下面介绍这些表模型的机制和适用场
景
（1）明细表（Duplicate Key）
机制：按指定列排序存储，数据完全保留（不聚合、不去重），支持任意维度查询。
适用场景：原始数据存储（如用户行为日志、设备埋点数据），需完整保留明细且查询维度灵活的场景。
（2）聚合表（Aggregate Key）
机制：按「聚合键」预聚合数据（如 sum、count、max 等），相同聚合键的新数据会合并旧数据。
适用场景：统计分析场景（如 PV/UV 统计、销售汇总），需高频查询汇总结果，且能容忍数据预聚合的场景。
（3）更新表（Unique Key）
机制：按「唯一键」去重，新数据覆盖旧数据（支持部分列更新），保证唯一键对应的数据唯一。
适用场景：需高频更新部分字段的场景（如订单状态更新、用户信息修改），更新维度固定且无需保留历史版本。
（4）主键表（Primary Key）（starrocks特有）
机制：支持主键级别的插入、更新、删除，提供行级事务一致性，数据按主键有序存储。

### Doris的unique 表是如何实现合并的？
Doris 的 Unique 表是类  LSM-Tree（Log-Structured Merge-Tree） 存储结构，数据写入时都是以追加方式生成新的版本
文件，不直接修改已有文件，保证高写入性能。然后依靠 Compaction 来完成数据去重与文件合并。
Compaction 会在后台自动运行，把同一个分片下的多个小文件读取出来，按照主键进行合并，相同主键只保留最新版本的
数据，旧版本数据会被清理掉。
合并完成后会生成一个完整的大文件，同时删除原来的小文件，这样既能保证主键唯一性，又能减少文件数量，提升查询
效率，还能回收存储空间。
Unique 表有MOW（ Merge-on-Write）和MOR（Merge-on-Read）两种 模式，这两种模式的主要区别就是数据写入后合并
的时机，MOW是写入的时候就进行合并了，保证了查询时候的性能。MOR是读取的时候才会合并数据。

### doris bitmap索引实现方式（华盛通/阿里小鹿中医/飞轮科技/京东健康）
Doris 的 Bitmap 索引是一种跳过索引（Skip Index），适用于中等基数（建议 100~100,000 之间）的列，如城市、职业等
字段。
实现原理：为每个不同的值维护一个 bit 数组，每一位对应一行数据，1 表示该行包含该值，0 表示不包含。查询时通过 位
运算（AND/OR/NOT）快速定位满足条件的行，跳过不相关的数据块，减少 I/O。
只支持等值查询和 IN 查询，不支持范围查询
只能建在单列上
适合正交查询（多条件组合过滤）场景，位运算效率极高

### Doris/Starrocks表应该如何设计？你从哪几个方面考虑？（跨越速运/壹向科技）
Doris 表设计主要围绕查询性能、导入效率、集群均衡、运维成本四个方面，从数据模型、分区、分桶、索引、字段类型、
键类型这几个方面设计：

### 选合适数据模型：明细用 Duplicate，更新用 Unique，聚合用 Aggregate；

### 合理分区：按时间分区，控制单分区数据量，便于冷热分离，删除和按照分区裁剪数据；

### 合理分桶：按高基数、查询频繁的维度分桶，避免数据倾斜，控制分桶数，充分利用BE并发能力；

### 设计键与排序键：将过滤、Join 字段设为前缀索引，提升查询效率；

### 索引选择：低基数列建 Bitmap，高基数用 BloomFilter，按照其他需求合理选择索引，减少不必要索引降低写入开
销。；

### 字段与类型：精简字段，使用小数据类型，减少存储与 IO。

### doris/starrcoks是如何创建前缀索引的？（跨越速运）
Doris 的前缀索引无需手动创建，是建表时自动生成的内置索引，不过需要注意使用方式：

### 自动创建：建表时，Doris 自动取 Key 列的前 36 字节作为前缀索引，无需任何额外语法。

### VARCHAR 截断规则：遇到 VARCHAR 类型列时，前缀索引立即截断，后续列不再纳入，且 VARCHAR 最多取前
20 字节。

### 一表只有一个：由于 Key 定义唯一，每张表只有一套前缀索引，因此建表时应将最高频的过滤列放在 Key 的最前
面。

### 变通方案：若某列不在前缀索引中但需要加速，可以：① 创建其他索引；② 对 Duplicate 表创建物化视图调整列顺
序，间接实现多前缀索引。

### Doris有哪些索引，该如何选择（必看，极其高频面试题）
Doris 的索引分两大类：
内置索引（自动维护，无需手动创建）

### Doris和starrocks 如何实现数据更新？（上海径赢）
在 Doris 和 StarRocks 中，数据更新不是直接修改磁盘数据，而是通过 追加写入新版本 + 逻辑覆盖（或删除标记） + 后台
合并 实现的。

### 底层机制统一是：写新版本，不改旧数据
更新或删除数据时，会写入一条新记录或删除标记（Delete Bitmap）。
查询时通过版本号 + 删除标记合并出最新结果。
后台通过 Compaction 清理旧版本，真正释放空间。

### 不同表模型支持更新方式不同
（1）在 Doris 中
表模型决定更新能力：三类表 — 主键（Unique Key）/聚合（Aggregate Key）/明细（Duplicate Key）。主键模
型是支持实时 UPSERT/部分列更新的核心；聚合表通过聚合函数（如 REPLACE）实现按 key 合并；明细表为纯追
加。
两种合并策略：写时合并（MoW，默认且推荐）与读时合并（MoR）。MoW 在写入时做去重合并，查询快；MoR
写入快但查询需在线合并，开销大。
更新/删除实现：
UPSERT（导入）：主键表通过导入（Stream/Broker/INSERT 等）实现 UPSERT，遇到相同主键覆盖旧行。
UPDATE/DELETE（DML）：执行时会扫描满足条件的行，然后写回新行或写入删除标记
（__DORIS_DELETE_SIGN__），查询时过滤，物理回收由后台 compaction 完成。DELETE 在不同模型下实
现（Delete Sign / Delete Predicate）。
（2）在 StarRocks 中
Primary Key 表（推荐用于高频更新）：主键表设计有主键索引 + DelVector（删除向量），写入时加载主键索引到内
存：对 Update 操作做 Delete（标记旧行） + Insert（写新行），并更新主键索引以指向最新数据文件与行号，查询
直接读取最新记录，无需在线合并，查询性能高，适合用 CDC 实时同步事务型数据。
Unique / Update 表（历史上用于更新）：以唯一键 + _version 语义实现“多版本取最新”的逻辑（REPLACE），写
入按批次产生版本号，查询取版本号最大的行；该表类型目前逐步被 Primary Key 表替代。

### Doris Stream Load原理浅析（度小满）
详细原理过程地址：https://doris.apache.org/zh-CN/blog/principle-of-Doris-Stream-Load
Stream Load是Doris用户最常用的数据导入方式之一，它是一种同步的导入方式, 允许用户通过Http访问的方式批量地将
CSV格式或JSON格式的数据导入Doris，并返回数据导入的结果，除此之外，也可以通过在客户端执行查询SQL来查询历
史任务的结果。另外，Doris还为Stream Load提供了操作审计功能，可以通过审计日志对历史的Stream Load任务信息进行

Stream Load具体执行流程如下：

### 用户提交Stream Load的Http请求到FE，FE対Http的Header解析（其中包括解析数据导入的库、表、Label等信
息），然后进行用户鉴权。如果Http的Header解析成功并且用户鉴权通过，FE会将Stream Load的Http请求转发到一
台BE节点，该BE节点将作为本次Stream Load的Coordinator；否则，FE会直接向用户返回Stream Load的失败信
息。

### Coordinator BE接收到Stream Load的Http请求后，会首先进行Http的Header解析和数据校验，其中包括解析数据的
文件格式、数据body的大小、Http超时时间、进行用户鉴权等。如果Header数据校验失败，会直接向用户返回
Stream Load的失败信息。

### 当上述数据校验都通过后，FE会生成任务生成导入计划，并且开启事务向Coordinator BE进行导数，Coordinator
BE接受到数据之后会通过BRPC同步至Executor BE，当Executor BE完成数据导入后，Coordinator BE通过Thrift
RPC 向FE发送Commit Transaction的请求。

### FE收到Coordinator BE发送的Commit Transaction的请求之后，会对事务进行提交， 并向Executor BE发送 Publish
Version的任务，如果Executor BE正常完成FE返回Commit Transaction，如果执行超时，FE返回Publish Version，
最终由Coordinator BE向用户返回Stream Load的最终结果。

### Doris 的Routine Load实现原理（度小满）
Routine Load使得Doris可以提供一个常驻的导入任务，可以不断的从指定的数据源读取数据，将数据导入到Doris中。其底
层是基于Stream load方式导入实现的。作为一个常驻形式的导入任务，Routine Load的每一次导入都会看成一个Task，每
个Task 由FE发送给BE执行, Task完成一批数据导入后通知FE，每批次的决定因素有最大超时时间/最大读取的条数/最大读
取的一批的大小，FE更新Offset后继续下发新Task，不断重复这个过程，从而完成数据写入。
其实现原理流程如下：
（1）FE 通过 JobScheduler 将一个导入作业拆分成若干个 Task。每个 Task 负责导入指定的一部分数据。Task 被
TaskScheduler 分配到指定的 BE 上执行。（task数量并不是无上限的，其主要是Doris集群任务的并发数/槽位数决定）
（2）在 BE 上，一个 Task 被视为一个普通的导入任务，通过 Stream Load 的导入机制进行导入。导入完成后，向 FE 汇
报。
（3）FE 中的 JobScheduler 根据汇报结果，继续生成后续新的 Task，或者对失败的 Task 进行重试。
（4）整个 Routine Load 作业通过不断地产生新的 Task，来完成数据不间断的导入。
优点：
高效性：Routine Load 使用分布式架构和并行处理技术，能够充分利用集群的计算和存储资源，以快速、高效地导入大规
模数据。
可扩展性：由于采用了分布式设计，Doris Routine Load 具有良好的可扩展性，可以根据需要增加节点，以应对不断增长的
数据导入需求。
注意事项

### 本质上还是调用的stream load任务，我们需要注意攒批的频次的设置，不能太过于频繁的去调用，避免未合并的版
本数超限。

### 什么是Doris的单副本导入机制？
在Doris进行数据导入时，首先将数据写入与Tablet相对应的MemTable中。当MemTable写满时，会将数据刷写（Flush）到
磁盘。刷写数据到磁盘的过程分为两个阶段：第一阶段将MemTable中的行存结构转换为列存结构，并生成每列的索引结
构；第二阶段将转换后的列存结构写入磁盘，生成Segment文件。
但是这样在多副本导入数据的时候就会需要在每个副本上执行MemTable的处理过程，从而使得每个副本所在的节点都会消
耗一定的内存和CPU资源，而且这种重复的处理也会降低执行效率。
为了解决这个问题，Apache Doris在2.0版本中引入了单副本导入的功能。该功能是通过从多个副本中选择一个主副本，然
后只对主副本进行计算，一旦主副本的数据文件全部写入成功，系统会通知从副本所在节点直接拉取主副本的数据文件，
实现了副本间的数据同步。当所有从副本节点拉取完成后，再返回成功或超时返回（大多数副本成功即返回成功）。这种方
式在很大程度上减轻了其他节点的负担，降低了计算资源和内存的使用，提高了整体系统的并发吞吐能力。

### 介绍下Doris Flink Connector 2PC 实现原理
Doris 的Flink Connector 2PC 的实现是将FLink 2PC 和 Doris Stream Load 2PC 进行结合实现的。首先，分别介绍下这两
个内容。
（1）FLink 2PC的实现分为预提交阶段和提交阶段。在预提交阶段，Flink 会在数据流中注入检查点分界线（Checkpoint
Barrier），将数据流划分为不同的检查点。每个算子会对当前的状态做一个快照，并保存到状态后端。Sink 端会以事务的方
式写数据到外部系统，比如 Kafka，并将事务 ID 保存到状态后端。在提交阶段，当检查点完成时，Flink 会通知所有的
Sink 算子提交事务，将数据写入到外部系统中。如果发生故障或崩溃，Flink 会从最近一次的检查点恢复，并根据事务 ID
回滚或重新提交事务，以保证数据不丢不重。
（2）Doris Stream Load 2PC的实现分为Prepare阶段和触发Commit阶段。在Prepare阶段，在 Prepare 阶段，
Coordinator BE 节点会向 FE 发送 Begin Transaction 请求，FE 会开启一个事务，并返回 Transaction Id 给 Coordinator
BE。然后，Coordinator BE 会向 FE 发送获取导入计划的请求，FE 会为 Stream Load 任务生成导入计划，并返回给
Coordinator BE。接着，Coordinator BE 会执行导入计划，将数据通过 BRPC 分发到其他 Executor BE 节点。Executor
BE 节点会将数据写入存储层，并执行 Prepare Transaction 将对应 Tablet 的数据写入事务添加到 TxnManager 中进行管
理。在 Commit 阶段，Executor BE 节点完成数据写入之后，Coordinator BE 节点会向 FE 发送 Commit Transaction 请
求，FE 会对事务进行提交，并向 Executor BE 发送 Publish Version 的任务，同时等待 Executor BE 执行 Publish Version
完成。Executor BE 节点会异步执行 Publish Version，将数据导入生成的 Rowset 变为可见数据版本，并执行 Commit
Transaction 将数据导入生成的新的 Rowset 添加到 TxnManager 中进行管理。Publish Version 正常完成或执行超时之后，
FE 向 Coordinator BE 返回 Commit Transaction 和 Publish Version 的结果。Coordinator BE 向用户返回 Stream Load 的
最终结果。
（3）Doris Flink Connector 2PC 在内存中维护读写的 Buffer，在启动的时候，开启写入，并异步的提交，期间通过 HTTP
Chunked 的方式持续的将数据写入到 BE，直到 Checkpoint 的时候，停止写入，这样做的好处是避免用户频繁提交 HTTP
带来的开销，Checkpoint 完成后会开启下一阶段的写入。
然后是在这个 Checkpoint 期间，可能是多个 Task 任务同时在写一张表的数据，这些都会在这个 Checkpoint 期间对应一个
全局的 Label，在 Checkpoint 的时候将这个 Label 对应的写入数据的事务进行统一的一次提交，将数据状态变成可见。
如果失败 Flink 在重启的时候会对这些数据通过 Checkpoint 进行回放。这样就可以实现了两阶段提交，保证 Doris 两端数
据的一致。

### 讲下Doris表关联物理关联的几种方式（跨越速运/深圳艾特尔/杭州织光映画科技/上海蓝

Doris 的 JOIN 物理执行有以下几种数据 Shuffle 方式：

### Broadcast Join：将右表全量数据广播到所有参与 JOIN 的节点，左表数据不动。网络开销 = N × T(右表)，适用范
围广但右表不能太大。

### Partition Shuffle Join：左右表数据都按 JOIN 条件列的 Hash 值重新分发到对应节点。网络开销 = T(左表) + T(右
表)，适用于通用场景。

### Bucket Shuffle Join：左表数据不动，只将右表数据按左表的分桶分布进行 Shuffle。网络开销 = T(右表)，要求
JOIN 条件包含左表的分桶列，且左表为单分区。

### Colocate Join：左右表数据都不移动，直接在本地做 JOIN。网络开销 = 0，要求两表属于同一 Colocation
Group，分桶列类型和桶数完全一致。
灵活性依次降低，但性能依次提升（前提是桶数足够多，并行度不受限）。此外，底层实现上支持 Hash Join（等值条件）
和 Nested Loop Join（非等值/笛卡尔积）两种算子。

### 介绍下 Doris/Starrocks SQL 解析流程
Doris sql解析是指将一条sql语句经过一系列的解析最后生成一个完整的物理执行计划的过程。其包括词法分析，语法分
析，生成逻辑计划和生成物理计划四个步骤。
（1）词法分析：主要负责将字符串形式的sql识别成一个个token，为语法分析做准备。
（2）语法分析：主要负责根据语法规则，将词法分析生成的token转成抽象语法树（AST）
（3）逻辑计划：负责将抽象语法树转成代数关系。代数关系是一棵算子树，每个节点代表一种对数据的计算方式，整棵树
代表了数据的计算方式以及流动方向。
（4）物理计划：指的是在逻辑计划的基础上，根据机器的分布，数据的分布，决定去哪些机器上执行哪些计算操作。
