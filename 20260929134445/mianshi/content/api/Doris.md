## Doris是什么？

doris是OLAP联机分析处理引擎

主流的OLAP引擎分为

MOLAP（多维 OLAP）：写入时预聚合数据，查询性能极致但灵活性有限（如 Kylin、Druid）；

ROLAP（关系型 OLAP）：无预聚合，依赖实时计算，查询灵活但性能依赖资源（如 ClickHouse、Presto）；

HOLAP（混合 OLAP）：融合前两者优势，聚合查询用 MOLAP，明细查询用 ROLAP（如 Doris、Starrocks）

### 那这里Doris/Starrocks 与 Clickhouse有什么区别？

主要的区别是在架构设计，数据一致性和对业务场景的侧重不同。

Doris/StarRocks采用的是分离式的MPP架构（PE/BE）

提供更简单的集群管理和更接近传统数据库的实时更新（通过主键进行更新或者事务）更适合高并发、BI 报表等场景

ClickHouse则采用中心化架构，对大规模集群的管理更复杂（依赖zookeeper协调分布式表和数据分片），但提供极高的查询性能，尤其是在单表查询和复杂分析场景中表现优异，数据更新为异步合并。适合单表大查询（join性能弱）和复杂分析等场景

### 但是在使用的过程中 ClickHouse 的 Join 性能为什么比starrocks/doris 差

这里主要是由于架构设计和功能特性的局限性

**架构上**

CK采用的是两层汇聚的执行框架，缺乏完善的 MPP 查询层，对复杂查询的支持较差，在大表之间的 Shuffle Join 场景下表现不佳

相比之下，Doris/starrocks 基于 MPP 架构，拥有完善的执行框架和向量化执行引擎，能够支持复杂的 SQL 分析，包括大小表的 Broadcast Join 和大表之间的 Shuffle Join

**Join 类型支持有限**

ClickHouse 仅支持 Global Join（对应Broadcast Join）和 Local Join（对应Colocation Join），在大表 Join 大表时，需要将右表广播到所有节点，性能受限

Doris/starrocks 支持四种 Join 方式，包括 BroadCast Join、Shuffle Join/Bucket Shuffle Join 和 Colocation Join，能够根据数据规模和查询类型选择最优的 Join 策略

优化器和索引不足：

ClickHouse 缺乏基于成本的优化器（CBO），无法对 Join 操作进行有效的优化。其聚合能力采用 Scatter Gather 模式的 2 阶段聚合，第二阶段为单节点，对内存和 CPU 的消耗较大

Doris/starrocks 拥有较完善的 CBO，能够根据数据分布和查询计划选择最优的执行方式。其聚合能力采用多节点并行聚合计算，结合 Runtime Filter 技术，进一步提高 Join

性能内存和数据处理能力：ClickHouse 的 Join 默认倾向于使用 Hash Join，要求右表能够完全加载到内存中构建哈希表。当右表过大时，会尝试将数据溢写到磁盘，导致性能显著下降

Doris/starrocks 在设计上考虑了更复杂的 OLAP 场景，通过分区分桶裁剪、点查索引（主键、倒排）等技术，进一步提高并发度和 Join 性能

### 问题：

#### 什么是mpp架构：

mpp（Massively Parallel Processing）是一种分布式数据处理技术，能将工作负载分散到多个节点上来提高数据处理性能。

在设计上，MPP架构优先考虑一致性（Consistency），其次考虑可用性（Availability），同时尽量做到分区容错性（Partition Tolerance）。

MPP架构常用于数据仓库、数据集市、大数据分析等场景

### Doris特点

高可用：Doris在数据存储和元数据管理方面采用了多副本机制和quorum协议，确保即使部分节点发生故障，集群还能稳定。而且还支持异地容灾部署(ccr)，可以通过双集群主备模式实现故障隔离

兼容性：Doris高度兼容mysql，像标准的sql语法都是支持的，还涵盖了大部分的mysql函数，所以可以轻松通过mysql可独断链接doris，包括迁移也是无缝支持。

实时数能力

这个事满足秒级写入和增量数据捕获，

灵活建模方式

提供多种建模方式，包括宽表建模、预聚合、星型/雪花模型等，支持灵活的数据组织方式

## 面试

#### 介绍下Doris或者Starrocks特点

这两个都是聚焦现代实时数据分析需求的数据库系统，融合了MPP（大规模并行处理）OLAP（在线分析处理）技术优势。简单来说就是简化数据分析流程，提升数据查询速度

特点的话

采用列式存储，只需要加载查询所需列的数据，大幅度的减少I/O操作

向量化执行引擎，传统事逐行处理的模式，这里实现数据批量化计算，提高计算速度和并发能力

还有的话智能索引技术，结合 Bitmap 索引与倒排索引，针对维度数据查询进行深度优化，进一步缩短查询响应时间

**分布式架构**数据在多节点间分布式存储，查询任务并行执行，既支持水平扩展以应对数据量增⻓，又保障了大数据场景下的高性能。

#### Doris / StarRocks 为什么会查询这么快？

Doris/StarRocks 查询快的核心原因，是它们围绕OLAP 场景（多维度分析、大表聚合、复杂查询）做了全链路的优化—— 从存储层减少 IO 开销、计算层提升处理效率，到查询层智能规划，每一步都是为了尽可能“减少无效数据、最大化硬件利用率”

1）整体架构：MPP架构 + 向量化执行：Doris 和 StarRocks 都是典型的MPP（Massively Parallel Processing）架构，查询时会把 SQL 拆分成多个并行的 fragment，在各个 BE 节点上并发执行。

2）存储层：列式存储 + 数据裁剪Doris 和 StarRocks 的存储层都是基于列式存储，同类数据连续存放，天然利于向量化计算。

Doris 和 StarRocks 的存储层都是基于列式存储，同类数据连续存放，天然利于向量化计算。

核心点在于：

列裁剪：查询只读取需要的列，其他列完全不扫描。

谓词下推（Predicate Pushdown）：过滤条件直接在存储层生效，能尽量减少 IO。前缀/Zone Map / Bloom Filter / MinMax 等索引：存储文件中带有列值范围（Min/Max），快速跳过不相关数据块

执行层：向量化执行引擎

Doris / StarRocks 的查询执行是向量化的，也就是一次处理一批数据，不像传统火山模型那样一行一行处理。

Pipeline 执行模型

新版本的 Doris和 StarRocks都引入了Pipeline 执行模型，这是一个巨大的性能提升点

Pipeline 模型允许不同算子之间异步并发执行，减少线程切换和等待，每个 pipeline 被划分为多个 task，能更好利用多核资源

## 整体架构

这里的话就是看整个doris的架构

首先来说我们一直有提到过一个mmp架构，哪什么是mmp架构？

MPP（Massively Parallel Processing，大规模并行处理），这个是一张高性能的计算架构

主要的作用就是用于处理大规模数据集和复杂查询

这个架构是采用多个独立计算的节点，每个节点都有自己的计算资源，通过分布式并行计算来加速数据处理

从下面的整个图来看，mmp有个主节点，下面会有各个计算节点，这些计算节点每个都有自己的独立计算资源，通过节点网络和主节点交互

整体来看MMP架构的特点可以概括为

分布式计算，这个没得说大数据都是这样的，只不过有一点区别于MapReduce/批处理模式的,节点是独立执行计算任务，最终合并结果

D大规模并行执行：查询被拆分成多个子任务，由多个节点执行，提升计算效率

横向扩展，MPP架构可以通过增加计算节点来提升整体计算能力

适用于复杂查询：擅⻓处理复杂 SQL 查询、OLAP（在线分析处理）任务，如聚合、关联分析、数据挖掘等

### 架构

主要是由FE和BE两部分组成（存算一体）

那这里

FE：是前端，主要负责接收和返回客户请求，元数据以及集群管理，查询计划生成等工作。

BE：是后端,主要负责的是数据存储和管理，查询执行计划等

这里整体的可以看作三层

第一层是Client Application  ，这层主要是应用，BI工具,JDBC链接等等

应用通过Mysql协议链接Doris （Doris 兼容MYSql协议）

#### 第二层就是到了FE这里，fe这里是无状态的计算层，里面有三个角色

**FE-Leader :**

唯一主节点，负责元数据管理（Catalog Manager）和查询优化（Query Optimizer） --总司令

这个是由Follower动态选举产生

**FE-Follower ：**

提供了元数据的读写服务，半数以上存活时候进行Leader选举

备用节点，Leader 挂了会选举为新 Leader

**FE-Observer：**

只读节点，不参与选举，只同步元数据用于分担读请求 --参谋（只看不决策）

用于扩展集群读的能力，不参与Leader选举

##### 哪这些角色之间是怎么保持元数据一致的？

元数据同步：Doris的FE节点通过内置的BerkeleyDB JE HA组件实现元数据的管理和同步，该组件采用类 Raft 协议（BDB JE 协议）保证元数据的一致性和高可用性。

这张图就是FE节点的元数据同步和高可用机制

**上半部分**

leader修改内存：比如用户执行了一条`CREATE TABLE`，Leader 先把这条变更应用到自己的内存元数据中

然后序列化log：同时把这条变更写成一条日志

再然后日志复制给其他节点：Leader通过网络把这条日志推送给Foolower和Observer

日志回放：Foolower/Observer 收到后，在自己的内存里重放这条操作，保证所有FE节点的内存元数据最终一致

**下半部分**

下半部分这里就是CheckPoint，这里解决的是日志膨胀的问题

因为上班部分的日志复制，日志会无限累计，新节点加入或节点重启时候，需要从第一条开始回访，可能由几千万条所以要解决这个问题

首先Leader定期去做快照，把当前内存中完整的元数据状态（所有表，分区，索引等信息）打包成一个image文件写入到磁盘中

接着Follower/Observer 拉取 image

先加载最新的image文件

再回放image生成之后的增量日志

这样新节点或重启节点就不需要回访全部历史日志

**总的来说上边部分保证实时一致，下半部分保证快速回复**

**这里FE其实只是负责解析SQL->生成执行计划->把计划下发给BE**

哪整体来说FE的功能主要是

**元数据管理：**FE负责整个Doris集群的元数据管理，包括数据库、表、分区、权限等！

**查询规划和调度：**FE接收用戶的查询请求，进行 SQL 语法解析、语义分析，并生成详细的查询执行计划。此后，FE 将该执行计划分发给 BE 节点

**集群管理：**FE 负责集群内 BE 节点的注册、健康状态监控和调度

#### 第3层这里 就是BE 这里就是干活的人

Execution Engine：执行 SQL 片段（比如做聚合、过滤、Join）

Storage Engine：实际存储数据（Doris 的数据分片 Tablet 分布在各个 BE 上）

##### BE的功能 --这个实在不知道什么意思 看遍视频

数据存储：BE负责的是数据实际存储的工作，Doris采用的是列式存储。它也支持行列混合存储

大大提升了再分析型查询中的性能表现。

#### Doris的存储形式

在Doris存储引擎中，数据时被分为成数据分片的，这个分片不是分区，可以叫做Tablet 也可以较成数据分桶。

同时每个Tablet又包含了若干个数据行

并且每个Tablet之间的数据没有交集，而且在物理上也是独立存储的。所以简单来说Tablet不论时逻辑上还是物理上都是独立的

##### Tablet和Partition的关系

多个 Tablet 在逻辑上归属于不同的分区（Partition）

一个 Tablet 只属于一个分区

**其实大白话就是partition可以有多个tabelt 但是tabelt只能有一个partition**

然后就是Tablet是移动数据，复制等操作的最小物理单元

Doris 中表名默认是大小写敏感的，这个可以设置，在第一次初始化集群配置的时候配置

lower_case_table_names为大小写不敏感的（只能是集群创建之后指定，后续不可修改！）

#### 存储名词

Tablet：这个是一张表的实际物理存储单元

RowSet：RowSet是Tablet中一次数据变更的数据合集，变更包括数据导入，删除，更新等

RowSet是按照版本信息进行记录，每次的变更都会生成一个版本

**注意：每个 Tablet 包括元信息及若干个连续的 RowSet。**

Version：这个我一开始理解成版本了，但是这个其实类似但不完全是，这个记录的是维护数据变更的记录信息。是

由 Start、End 两个属性构成，表示的是RowSet的版本范围

Segment：这个是表示RowSet 中的数据分段，segment存储了列的实际数据以及一些索引数据。多个 Segment 构成一个 RowSet

Compaction:连续版本的 RowSet 合并的过程成称为 Compaction,合并的过程会进行压缩

#### 表模型

**表模型这里分为三个：明细模型，主键模型和聚合模型**

明细模型：Duplicate Key 允许指定的Key列重复，Doris存储层保留所有写入的数据，这种适用必须保留所有原始数据记录的情况。 这在日志非常常见的

这里排序键也可以不选择，没有需求就可以不用做。

"enable_duplicate_without_keys_by_default"= "true"

主键模型：Unique Key每一行的Key值唯一，可以确保指定的key没有重复值，Doris 存储层对每个 key 只保留最新写入的数据，适用于数据更新的情况。

这个说白了类似mysql的根据时间更新一样，当用户更新一条数据时，新写入的数据就会覆盖具有相同key的旧数据。

这里有两个实现方式：

1.读时合并：merge-on-read 这个就是用户在写入的时候不会触发任何的去重，和明细差不多，但是在查的时候，所有的数据去重操作都在查询或者compaction 进行。这个就是写好读差，内存消耗高。

2.写时合并(merge-on-write)：这个就是和上面相反呗。

聚合模型：Aggregate Key  可根据 Key 列聚合数据，Doris 存储层保留聚合后的数据，从而可以减少存储空间和提升查询性能；通常用于需要汇总或聚合信息（如总数或平均值）的情况

这里Doris将表中的列分为了Key和Value两种，聚合模型的数据会根据维度列（key）进行分组，并对指标列（value）进行按照指定的聚合函数进行聚合。

像平常的求和啊，max，min bitmat_union位运算，非空替换等等都能做

#### 表结构变更

这里的意思就是允许用户在不中断查询和写入的前提下，修改表的结构定义，主要是对列的修改和索引的改动

在了解之前要知道名词

Base Table：基表。每一个表被创建时，都对应一个基表。

Rollup：基于基表或者其他 Rollup 创建出来的上卷表。Index：物化索引。

Rollup 或 Base Table 都被称为物化索引。

Transaction：事务。每一个导入任务都是一个事务，每个事务有一个唯一递增的 Transaction ID。（后面课程有事务机制的详细解释

轻量级别的变更：

这个是1.2.0版本推出的，是专门替换 Hard LinkedSchema Change

Hard LinkedSchema Change有三个核心问题

**第一个是等待导入导致耗时增加：**Hard Linked需等待当前导入任务完成才能执行变更，集群规模或数据量越大，等待时间越⻓

**第二个是导入双写损耗：**变更期间为保证事务性，需对新旧 Tablet 双写数据，占用额外 IO 资源，或迫使用戶在 “等待变更”与 “接受双写” 间二选一

**第三个不兼容 Delete Predicate：**若表存在标记删除（Delete Predicate），Hard Linked 会降级为 Sort/Direct SchemaChange，需重写全表数据，失去轻量优势。

所以Light Schema Change 的核心就是 仅修改FE元数据，不涉及BE物理数据重写或者文件关联，全程不用和BE节点交互，仅通过FE元数据更新就能实现变更

流程大致就是：接收加减Value列的DDL请求后，FE直接修改并持久化表的元数据，无需创建新的Tablet,也无需关联数据文件，也不用导入，等元数据更新完就能生效

这里比较适用于新增/删除非主键列，修改varchar类型长度，重命名列这些

对于重量级变更：

其实就是区别于上面Light Schema Change的另外一种schema变更方式，不支持轻量级别的就使用这种

整体的流程

用户提交修改表

首先到FE这里

第一步创建SchemaChangeJob ，然后创建新的Tablet

接着到BE，BE这里有旧的Tablet哪这里会创建一个新的Tablet

把旧的数据同步到新的Tablet里，写入到新的里之后会执行一致性检查没问题就同步完成

然后带FE里进行元数据切换，把新的Tablet生效，同时标记旧的Tablet删除

#### 分区分桶策略

在Doris里用户的数据会被划分成若干个分区，划分是按照指定的分区列进行划分比如时间划分

然后每个分区内在进一步的做分桶，每个分桶就是一个数据分片-Tablet，这个也是数据划分的最小逻辑单元

这个最小单元包括了数据的移动，复制等操作

Partition可以视为是逻辑上最小的管理单元。数据的导入与删除，都可以或仅能针对一个Partition进行

#### 索引

Doris的索引分为两部分

内建智能索引：

这里就是排序键了，Doris会按照排序键有序的存储数据，并且每行数据的前36个字节都会创建一个前缀索引。这样来减少扫描范围

ZoneMap 索引：这个是在列上自动维护的索引信息，包括每列的max/min null个数等等，这个索引在段和页面级别生效，记录了Page和Segment内每列的最值，这个用户感知不到

用户创建的二级索引：

这个二级索引是需要手动创建的

比如布隆过滤器索引（BloomFilter Index）：

基于 Bloom 在 1970 年提出的多哈希函数映射快速查找算法，用于快速判断元素是否属于集合，但存在误判的可能性

N - Gram 索引（N - Gram BloomFilter Index）： 2.0开始支持，主要用来提升LIKE查询的性能

位图索引（Bitmap Index）：

用位图表示索引，每个键值对应一个位图，占用存储空间小，创建和使用速度快，但修改操作锁粒度大，不适合频繁更新的场景。
