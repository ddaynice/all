## Zookeeper的选举过程

"Zookeeper 的选举得票数超过半数的节点成为 Leader。选举过程是一个动态协商的过程，我分几个关键点来说。

（讲投票内容）

首先，每个节点启动时会先给自己投一票。这一票包含两个核心信息：myid（节点的唯一标识）和 ZXID（事务 ID，代表数据新鲜度）。

选举的比较规则是：先比 ZXID，ZXID 大的优先；ZXID 相同则比 myid，myid 大的优先。这样设计是为了保证选出的 Leader 数据最新，不会丢数据。

（讲动态过程）

选举不是投一次就定死的，而是一个互相交换、动态改票的过程。

假设 5 个节点，myid 分别是 1 到 5。节点 1 先启动，投自己一票，但只有 1 票没过半数（5 台需要 3 票），进入 LOOKING 状态。节点 2 启动，也投自己，然后和节点 1 交换投票信息，发现对方得票一样，但 myid=2 更大，于是节点 1 改票投给 2。

节点 3 启动后，和 1、2 交换信息，1 和 2 发现 3 的 myid 更大，都改票投给 3。此时 3 获得 3 票，超过半数，成为 Leader。后面启动的 4、5 发现已经有 Leader，直接作为 Follower 加入。

（讲乱序和过半数）

即使启动顺序是乱的，规则也一样。比如 5 先启动，2 和 3 随后启动，它们互相比较后会发现 5 的 myid 最大，都改票投给 5，5 获得 3 票成为 Leader。

这里的关键是过半数机制。5 个节点必须获得至少 3 票才能当选，这是为了防止脑裂——任何时候最多只有一个节点能获得过半数支持。

## 什么是Zookeeper

"Zookeeper 是 Apache 的顶级项目，本质上是一个分布式协调服务。它不是用来存储业务数据的，而是用来解决分布式集群里节点之间的一致性协调问题。

（讲核心定位）

在分布式系统里，多个节点分布在不同机器上，网络可能抖动，节点可能宕机。节点之间怎么知道谁是老大、配置变了怎么同步、多个节点同时操作一个资源怎么不冲突——这些'协调'问题，就是 Zookeeper 要解决的。

（讲数据模型）

Zookeeper 的数据模型是树形的 ZNode 结构，类似 Linux 的文件系统目录。每个 ZNode 可以存少量数据，默认不超过 1MB，所以也有人称它为'分布式小文件存储系统'。

它的核心机制是Watcher 监听。客户端可以监听某个 ZNode 的变化，比如配置节点被修改了、某个服务节点下线了，Zookeeper 会主动推送给客户端，实现集群状态的实时感知。
