## HDFS的组成原理

Hadoop 的核心架构从 1.x 到 2.x 有一个重要演进，我结合这张图来说。

（讲 1.x）

Hadoop 1.x 主要由 HDFS、MapReduce 和 Common 组成。这里最关键的问题是，MapReduce 同时承担了计算和资源调度两个职责。它既要跑用户的业务逻辑，又要管理集群的 CPU、内存分配。这样导致几个弊端：一是 MapReduce 一家独大，其他计算框架很难接入；二是资源管理和计算逻辑耦合，升级维护困难；三是 JobTracker 存在单点瓶颈，集群规模大了以后调度能力跟不上。

（讲 2.x）

到了 Hadoop 2.x，架构上最大的变化是引入了 YARN，把资源调度从 MapReduce 中完全剥离出来。YARN 作为独立的资源管理平台，负责集群资源的统一管理和分配。MapReduce 退化为一个纯粹的计算框架，只负责跑分布式计算任务。

## HDFS读写流程

#### 一、写流程（重点：Pipeline 机制）

（面试官：HDFS 怎么写数据？）

"HDFS 的写数据过程，核心是两个机制：NameNode 分配位置，DataNode 流水线传输。

（第一步：找 NameNode 申请）

客户端先通过 DistributedFileSystem 向 NameNode 发起写请求。NameNode 会做一系列校验：文件是否已经存在？父目录是否存在？用户有没有写权限？校验通过后，NameNode 返回可以上传。

（第二步：NameNode 分配 DataNode）

客户端告诉 NameNode 要上传第一个 Block。NameNode 根据机架感知策略，返回 3 个 DataNode 的地址，比如 DN1、DN2、DN3。选择策略一般是就近原则——优先选离客户端近的节点，再选不同机架的节点，保证副本分布的可靠性。

（第三步：建立 Pipeline）

客户端拿到 3 个地址后，和 DN1 建立连接。DN1 收到数据后，不是存完再转发，而是边收边转发给 DN2，DN2 再边收边转发给 DN3。这样就形成了一个数据流水线（Pipeline）。

（第四步：Packet 为单位传输）

客户端把 Block 切成一个个 Packet（默认 64KB），先发给 DN1。DN1 收到一个 Packet 后，同时做两件事：一是写入本地磁盘，二是转发给 DN2。DN2 同理，写入本地再转发给 DN3。

（第五步：ACK 确认）

DN3 写完后，返回 ACK 给 DN2；DN2 写完后返回 ACK 给 DN1；DN1 写完后返回 ACK 给客户端。客户端收到 DN1 的 ACK，就认为这个 Packet 写入成功了。

（一句话总结写流程）

所以写流程的核心是：NameNode 指路，DataNode 流水线接力，Packet 为单位边写边传。

#### 二、读流程（更简单）

（面试官：HDFS 怎么读数据？）

"读流程比写简单。

客户端向 NameNode 请求下载文件，NameNode 校验权限和文件存在性后，返回这个文件所有 Block 所在的 DataNode 地址。

客户端根据就近原则（优先选离自己近的、负载低的节点），挑选一个 DataNode 建立连接，直接读取数据。读的时候也是按 Packet 为单位，客户端本地缓存后写入目标文件。

如果一个 DataNode 读失败了，客户端会自动切换到另一个有副本的 DataNode 继续读，对业务透明。

#### 三、容错机制（加分项）

（面试官：写入过程中 DataNode 挂了怎么办？）

"HDFS 在写入过程中有完善的容错机制。

第一种情况：Pipeline 中某个 DataNode 挂了。

比如 DN1→DN2→DN3 的流水线，写到一半 DN2 挂了。此时 Pipeline 会立即关闭，把 DN2 从管道中移除，剩下的 DN1 和 DN3 继续以管道的形式传输。同时 NameNode 会感知到 DN2 挂了，分配一个新的 DataNode 来保持副本数量。

第二种情况：客户端和 DataNode 通信中断。

客户端会断开连接，转而从存储这个 Block 的其他 DataNode 读取数据，并且会记录这个有问题的 DataNode，后续不再从它读取。

第三种情况：数据损坏。

每个 Block 都有校验和（Checksum）。客户端读取数据时，会计算校验和并与存储的校验和比对。如果不一致，说明数据损坏了，客户端会从其他副本读取，同时通知 NameNode，NameNode 会标记这个副本为损坏，并触发副本复制。

## HDFS的副本和块机制(☆☆☆)

### HDFS为什么文件要分块进行存储管理？

因为一个文件有可能大于集群中任意一个磁盘，块机制就是相当于能把数据存进去，解决了这个问题

然后块也是非常适合用于数据备份进而提供数据容错能力和数据的可用性

### HDFS块是多大？为什么设置这么大

这个块默认是128m2.x版本之后

但是实际使用的话会更大

设置这么大是因为最小化寻址开销，如果块足够大，从磁盘传输数据的时间会明显大于定位这个块开始位置所需的时间，其实随着磁盘速率的提升，块的大小也会增加。

你这个块设置太小，会增加寻址时间，程序一直在找块的开始位置

太大的话，从磁盘传输数据的时间会明显大于定位这个块开始位置所需要的时间

简单来说就是HDFS块的大小设置主要取决于磁盘传输速率。

## 什么是小文件问题，怎么处理

HDFS 的 Block 默认 128MB，但一个文件无论多小，都会独占一个 Block 的元数据记录。比如一个 1KB 的日志文件，它只占 1KB 磁盘，但 NameNode 内存里要存一份完整的元数据（文件名、权限、位置等）。

小文件过多会带来三个主要问题：

NameNode 内存压力。NameNode 把所有文件和 Block 的元数据存在内存里。如果集群里有几百万个小文件，NameNode 内存会被撑爆，GC 频繁，甚至 OOM

MapReduce 计算效率低下。默认的 TextInputFormat 下，一个文件对应一个 Map 任务。如果输入是 100 万个小文件，就会产生 100 万个 Map 任务。每个任务只处理几 KB 数据，但 JVM 启动、资源申请的开销远大于实际计算时间，集群资源大量空转。

查询性能下降。读取时需要频繁和 NameNode 交互定位 Block，磁盘寻道次数也多，整体吞吐下降。

解决的办法其实就是修改默认的切片机制，例如使用CombineTextInputFormat切片机制作为 MapReduce 的输入格式，它会把多个小文件合并成一个 Split，让一个 Map 任务处理多个小文件，减少 Map 任务数量。

存储格式层面。把小文件合并成 SequenceFile、Parquet 或 ORC 这类列式格式，既减少文件数量，又提升查询效率。

## HDFS中datanode之间怎么保证备份数量的同步？

HDFS 主要通过Block Replication（数据块复制）和Block Rebalancing（数据块均衡）来确保 DataNode 之间的副本同步。

HDFS 保证副本同步是分三层来保障：写入时保证、运行时监控、长期均衡。

（第一层：写入时）

首先是写入时的 Pipeline 级联复制。客户端写数据时，NameNode 通过机架感知策略选出 3 个 DataNode。然后建立流水线：客户端先把数据写给第一个 DN，第一个 DN 边存边转发给第二个，第二个再转发给第三个。三个副本都写成功后，这次写入才算完成。如果中间某个节点挂了，NameNode 会立即分配一个新节点来补充，保证最终是 3 个副本。

（第二层：运行时监控）

第二是运行时的 Block Report 监控纠偏。DataNode 会定期向 NameNode 发送 Block Report，汇报自己存了哪些数据块。NameNode 拿这份报告和内存里的元数据比对，如果发现某个 Block 副本数不足——比如某个 DataNode 挂了导致只剩 2 个副本——NameNode 就会触发复制，找一台健康的 DataNode 把缺失的副本补回来。反之，如果副本数超了，也会触发删除。这个机制保证了副本数量在长期运行中始终维持在设定值。

（第三层：长期均衡）

第三是数据均衡。集群运行过程中，新节点加入或者数据写入不均匀，会导致某些节点磁盘快满了，某些节点还很空。HDFS 提供了 Balancer 组件，NameNode 会启动 Balancer 进程，把 Block 从负载高的节点迁移到负载低的节点，确保数据在集群中均匀分布，避免单点瓶颈。
