## 说一下你对Hadoop的理解？

"Hadoop 是 Apache 开源的分布式系统基础架构，本质上是解决海量数据存储和海量数据计算这两个核心问题。

其实我感觉更像一个软件包，需要什么就往里面装什么

它主要由三个核心模块组成：

（讲 HDFS）

第一个是 HDFS，分布式文件系统。它的作用是为海量数据提供存储。文件太大存不下，HDFS 会自动把文件切分成块，分散存到多台机器上，每个块默认存 3 份副本保证可靠性。对用户来说，就像操作一个超大号的硬盘，不用关心数据到底存在哪台机器上。

（讲 MapReduce）

第二个是 MapReduce，分布式计算框架。它的作用是为海量数据提供计算能力。核心思想是"分而治之"：把一个大计算任务拆成很多小任务（Map 阶段），发到各个节点并行计算，然后再把结果汇总（Reduce 阶段）。这样一台机器算不动的任务，十台机器一起算。

（讲 YARN）

第三个是 YARN，集群资源管理系统。Hadoop 2.0 之后引入的，负责统一管理集群的 CPU、内存等资源。以前 MapReduce 自己管资源，耦合太紧；YARN 把资源管理和计算逻辑解耦了。现在不管是 MapReduce、Spark 还是 Flink，都可以跑在 YARN 上，由 YARN 统一调度资源。

（讲关系和设计思想）

这三个组件的关系是：HDFS 负责存储，MapReduce 负责计算，YARN 负责资源调度。它们既可以独立使用，也可以配合起来用。

Hadoop 最核心的设计思想是存算分离。存储层和计算层是独立的，后来 Spark 计算性能比 MapReduce 快很多，但 Spark 可以直接读 HDFS 上的数据，不需要重建存储层。这种解耦设计让 Hadoop 生态非常灵活。

## 什么是shuffle?

shuffle就是map方法之后，reduce之前的处理过程就是shuffle!

是将map的结果二次分发到reduce的过程

## shuffle的整体过程

collect->map->collect->spill->combine

这是整体的流程

首先客户端会获取待处理的文件，然后根据客户端与集群的参数配置，形成一个任务分配规划。

然后会调用submit方法，把要执行的jar包,job信息，分片信息提交到hdfs上

紧接着就会把程序提交到yarn集群上运行，yarn就是生成一个进程（mrappmaster）

这个进程是用来控制maptask和reducetask的启动

这个是因为分片信息我们已经提交到了hdfs上，那么MrAppMaster就会去获取这个分片信息，去计算出maptask的数量

这个时候maptask通过我们写的RecordReader，会解析出来一个一个的k/v

第二步这里maptask会将解析出来的k/v交给map函数进行处理，然后回产生新的k/v

这个时候maptask会将新的k/v收集起来写到环形缓冲区里

第三步这里当环形缓冲区到了80%以上就会打开流，会把数据写道本地文件系统磁盘上，并且生成一个临时文件，然后关闭流。这个过程是重复的，只要80%了又会重新打开，然后开始溢写。

所以这里可能会生成多个临时文件，同时在写入本地磁盘之前，会先对数据进行一次本地排序。

第四步当所有的数据处理完之后maptask会对所有的临时文件一次合并，以确保最终只会生成一个数据文件。在进行文件合并的过程中，maptask会以分区为单位及逆行合并，对于某个分区，他将采用多轮递归合并的方式

在溢出过程中，及合并的过程中，都要调⽤  partitoner  进⾏分组和针对  key  进⾏归并排序

第五步这里就是reduce了

reduce这里两步走先copy数据在merge+sort

reduce任务通过HTTP向各个Map任务拖取它所需要的数据

这里每个节点都会启动一个常驻的HTTP server,其中这里的一项服务就是响应Reduce 拖取 Map 数据。

### 注意：

在shuffle的时候map任务将输出结果写到本地磁盘，因为map输出的是中间结果，所以等到reduce 处理完之后，会从本地磁盘删除，所以说他没有必要上传到hdfs上，因为你上传hdfs上他还要有副本对吧。

这也是MapReduce ⽐ Spark 慢的原因之一。

你spark是将中间结果缓存到内存里，再次使用的时候直接加载，比从磁盘里去读快多了！

shuffle的缓冲区的大小会影响到mr程序的执行效率，原则上来说缓冲区越大，磁盘的io就越少，执行的速度就越快。可以用参数去设置，我习惯是1024mb

## 为什么需要 shuffle? 什么场景需要 shuffle?( ☆☆☆ ) 

### 什么是 shuffle, 谈谈你对其的理解？

其实shuffle的目的就是将map端处理的结果二次分发给reduce端进行处理。比如说将所有的map结果按照key进行hash散列到不同的reduce上处理，保障使得同样的key进⼊相同的reducer进⾏聚合处理。

shuffle 移动了⼤量的数据，对计算、内存、⽹络和磁盘都有巨⼤的消耗，因此，只有确实需要 shuffle 的地⽅才应该进⾏ shuffle ，否则尽可能避免 shuffle 。这也是为什么有些任 务能只在 map 端完成就在 map 端完成，因为此时不需要 Shuffle ，效率会⾼。

### 可不可以不用shuffle？

可以，那就是Map-Only每个节点读自己的数据，过滤后直接输出

但只要你的计算逻辑需要"跨节点看同一份数据"，就逃不掉

只要是涉及到了网络的一个拉去的一个动作的话，比如说从不同节点上去拉取数据的话，它其实都是需要p的，还比如说我们的一个排序。我们的一个join等等，这些都是需要的。

## 为什么在Map和Reduce阶段系统默认必须要对Key进行排序？(☆☆☆）

因为reduce阶段是将相同key的文件进行合并，如果不对key进行排序，就需要一个一个判断是不是相同的key，这会导致reduce阶段排序压力大，拉低效率

而按照key排序之后，只需要和后面的相比看是不是相同的key，如果不一样，直接将前面相同key的一组拿走进入到recue效率高

其实 Map 端排序是"顺便"做的，代价极低

MapTask 的排序发生在内存缓冲区溢写磁盘前（Spill 阶段），数据量小。如果不排序直接写磁盘，后续 Reduce 拉取数据时还是要排序，而且跨网络排序成本更高。Map 端预排序是"花小钱办大事"。

## shuffle过程有几次排序，几次落盘？(☆☆☆)

4次排序，3次落盘

maptask：2次

reducetask:3次

对于maptask

溢写：它会将处理结果暂时的放到环形缓冲区里，当缓冲区达到阈值后，在溢写之前，会对缓冲区的数据进行一次快速的排序，然后将这些有序的数据溢写到磁盘上！这是第一次排序，第一次落盘

归并：这里maptask将数据处理完之后，会对磁盘上所有文件进行归并排序！这是第二次排序

对于Reducetask

它从每个maptask上拷贝相应的数据文件，这里会先溢写到内存里，如果文件的大小超过阈值，就溢写道磁盘中，否则就存到内存中！这是第2次落盘

如果磁盘的文件数目达到一定的阈值，就进行一次归并排序，这是第三次排序,来生成一个更大的文件

如果内存中的文件大小或者数目超过一定阈值，则进行一次合并后将数据写道磁盘上，这是第三次落盘

当所有的数据拷贝完之后，Reducetask会统一对内存和磁盘上的所有数据进行一次归并排序，这是第4次排序

## MR中Map Task的工作机制(☆☆☆)

上面说了这么多的其实工作机制也比较明朗，这里总结下

首先是读，这里是读取数据，读取数据的组件 InputFormat (默认 TextInputFormat) 会通过getspill方法对输入目录中的文件进行逻辑切片规划得到block，这里又有多少个block就会启动多少个maptask

然后上一步将输入的文件切分成block之后，由RecordReader 对象 (默认是LineRecordReader) 进行读取

是以\n作为分隔符读取一行数据，返回kv， Key 表示每行首字符偏移值，Value 表示这一行文本内容这里上面也有说

然后这里是第三步了，读取block返回kv后，进入用户自己继承的Mapper类中，执行用户重写的map函数，RecordReader 读取一行这里调用一次

再然后Mapper 逻辑结束之后，将 Mapper 的每条结果通过 context.write 进行collect数据收集。在 collect 中，会先对其进行分区处理，默认使用 HashPartitioner

上面的步骤其实都是shuffle之前的步骤

接下来，会将collect的数据写入到内存中，内存中这片区域就是我们说的环形缓冲区默认是100mb，这个环形缓冲区的作用就是批量收集mapper结果，减少磁盘io的影响。我们的kv以及对应的partition结果都会被写入到缓冲区里，写之前k和v都会被序列化字节数组

当环形缓冲区的数据溢写达到80%，溢写的线程就会启动，需要对这80%的空间内key进行排序，这个排序是默认的行为，也是对序列化字节做的排序

最后就是合并溢写文件，每次溢写都会在磁盘生成一个临时的文件，写之前会判断是否由combiner，如果mapper的输出结果真的很大，有多次这样的溢写发生，磁盘上相对应的就会出现很多的临时文件存在

当整个数据处理结束之后会对磁盘中的临时文件进行merge合并，因为最终的文件只有一个写入磁盘，并且为这个文件提供索引文件，这是来记录每个reduce对应数据的偏移量

## 请说下 MR 中 Reduce Task 的⼯作机制 ( ☆☆☆ )

之前我我们说的reduce只是说了copy阶段，其实在整体来说

分为copy sort reduce三个阶段，重点是在前两个

copy阶段包含一个eventFetcher来获取已经完成的map列表，由Fetcher线程去copy数据，

在这个过程会启动两个merge线程，分别为inMemoryMerger和onDiskMerger

分别将内存中的数据menge到磁盘和将磁盘中的数据进行merge，待数据copy之后，copy阶段就完成了

接下来就是sort1阶段了，sort1阶段主要是执行finalMerge操作，完成之后就是reduce阶段，调用用户自定义 的reduce函数进行处理。

这里的详细步骤：

首先是copy阶段：简单的拉取数据，reduce进程会启动一些数据copy线程，通过http反射光hi请求maptask获取到属于自己的文件

哪这里maptask的分区会标识每个maptask属于哪个reducetask,默认reducetask标识是从0开始的。

接着就是merge阶段了：在远程拷贝数据的同时，reducetask这里会启动两个线程对内存和磁盘上的文件进行合并，防止内存使用过多或者磁盘上文件过多

merge 有三种形式：内存到内存；内存到磁盘；磁盘到磁盘。

默认情况下第⼀种形式不启⽤。当内存中的数据量到达⼀定阈值，就直接启动内存到磁盘的 merge 。

与 map 端类似，这也是 溢写的过程，这个过程中如果你设置有 Combiner ，也是会启⽤的，然后在磁盘中⽣成了众多的溢写⽂件。

内存到磁盘的 merge ⽅式⼀直在运⾏，直到没有 map 端的数据时才结束，

然后 启动第三种磁盘到磁盘的 merge ⽅式⽣成最终的⽂件。

然后就是合并排序：把分赛的数据合并成一个大的数据后，还会对合并后的数据排序

最后这里会对排序后的键值对调用reduce方法：键相等的键值对调用一次reduce方法，每次调用会产生零个或者多个键值对，最后把这些输出的键值对写入到HDFS上

磁盘，io网络开销都会增加

## MR跑的慢的原因：：减少落盘次数，那不落盘的话，数据放在哪⾥，是内存吗？

对MR慢的原因就是磁盘I/O过多，每个阶段（ Map -> Shuffle -> Reduce ）都需要将中间数据落盘

如果减少落盘次数，哪数据就需要放到内存，但是MR是基于磁盘计算，默认不会放到内存里。

SPARK采用的是RDD存在内存中，所以计算速度会比MR块很多

但是spark为什么会比MR块？

spark默认将中间结果刚到内存，大大减少了磁盘i/o

任务失败时候，RDD采用血缘机制重新算，只需要重新计算丢失的就行，但是MR需要重新算整个任务

DAG有向无环图优化执行计划，这种避免了MR的多次落盘的问题

## 没有排序需求就可以使⽤ hashshuffle 吗？

首先什么是hashshuffle，这个是一种基于哈希分区的数据传输方式

是先每个map任务计算之后，通过hash函数将数据分配到不同的reduce任务对应的分区

每个reduce任务只需要拉取自己对应的分区数据，并进行处理

这里的话传输数据不会进行排序，也不需要复杂的合并，

哪这里再使用hashshuffle的前提就是：不需要排序

比如goup by 不要求有序,连接操作（ Join ）  ——  只要  Join  逻辑不依赖排序，使⽤  hashPartitioner  即可。
