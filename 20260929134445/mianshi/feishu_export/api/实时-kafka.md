###### 消息队列

消息队列是一种在分布式计算环境中使用的技术，用于在不同的进程或服务之间传递 消息。

整体来说消息队列也是有着属于自己的特点

1.队列结构，队列结构的特点就是先进先出，后进后出，有个比较的对象就是堆，堆我们说是一端是封起来的！像一个杯子一样，先进去的后出来

2.可以允许异步处理，比如现在生产者生产了一条消息放到队列，如果说我想在生产下一条，必须是要等到消费者消费完这一条数据，才能生产，这种就是同步

异步就是现在消费队列里有数据，但是我不用等他是不是被消费了！

3.应用解耦，这个就是我们经常说的耦合性高，耦合性就是千丝万缕的关系！类似剪不断理还乱的关系，在我们这里具体的体现就是，改一处而动全身，这种情况我们往往是说功能解耦。你的改动并不会影响到我

在生产者和消费者中的体现就是，不管是几个生产者或者生产者是什么配置，都不会影响到消费者，就是你改你的我改我的，我俩之间不会有影响，这种就是解耦

4.负载均衡

5.可靠性保障，比如说放到内存，已关机就没了，其实就是保存到磁盘上，有一定的保障

6.流量削峰：

消息本质上就是一种媒介

#### 关系

整体的梳理一遍这些关系

• Topic：逻辑概念，可以理解成“表”或者“消息队列的名字”。

• Partition：Topic 的物理切分单元，一个 Topic 可以配置 N 个分区。

• Replica：每个分区又可以配置 M 个副本（leader + followers）。

• Broker：Kafka 进程，真正存数据、跑网络 IO 的机器。

topic是逻辑上的比如128mx3 代表有3个文件，那这个3就是partition，相当于topic是partition的超链接

**用一句话来说就是：**

每个分区（Partition）的每个副本（Replica）最终都要落到某一个 Broker 的某个 log 目录下。

Topic 自己不直接“放”在 Broker 上，而是被拆成很多“分区副本”，这些副本被“调度”到 Broker 上。

**Topic 是逻辑命名空间，Partition-Replica 才是物理实体，最终被调度到 Broker 的 log 目录下。**

比如

topic = 一份报纸

Partition = 报纸的版面（A1、A2、B1…）

Replica = 每块版面的印刷厂复印件，北京印 3 份，上海印 2 份

Broker = 印刷厂

北京厂（Broker-1）可能同时存了 A1(leader)、A2(follower)、B1(leader) 这些副本；上海厂（Broker-2）存了 A1(follower)、A2(leader)……

这样 Topic 的“容量”跟“可用性”就分散到了多家印刷厂（Broker）。

Topic 是“逻辑名”，分区副本是“物理文件”，Broker 是“文件柜”；Producer / Consumer 只跟“文件柜里的 leader 文件”打交道，Follower 只是做备份，ZK（或 __consumer_offsets）只是记账的。

### Broker 

用一句话来说，Broker 就是kafka的一个服务器节点，一个物理的概念

Broker 是指 Kafka 集群中的一个物理节点，负责处理客户端请求、同时也处理客户端 发送数据的存储与复制。**Kafka 集群由多个 Broker 节点组成，并且****每个 Broker 都有全 局唯一的 id 标识。**

#### **Controller（控制器）**

在我接触到的集群，是分为两类的！主从，主备

但是在kafka集群中各个**Broker 之间是没有这种关系的角色**

分区Leader角色承担与Producer和Consumer的读写 交互，而Follower会从Leader分区中进行数据同步

如果说网络问题，或者broker本身的问题导致的，说我的Follower或者Leader无法正常交互，按照ISR副本机，如果出现故障长时间没有与leader进行通讯，那么这个节点就会被踢出ISR

所以kafka提供了一套机制，如果出现故障我们该如何应对

这里主要就两类

#### 1. Leader 故障处理

根据Leader的选举规则：在ISR中存活为前提，按照ISR中排在前面的优先。例如 AR[1,0,2]，ISR[1，0，2]，那么 leader 就会按照1，0，2的顺序轮询。**第一次leader的顺序是1，这个1的leader挂了之后 再选就是0成为leader 在下一次就是2  选举是从ISR中选的  ****AR就是一个分区的所有副本集 ISR是存活的副本，和leader沟通的副本**

**AR：一个分区中的所有副本集就是AR**

**ISR:可以与leader节点进行通讯，及时同步副本的叫做ISR**

假如之前的 leader 在broker1 上，那么如果leader故障，那么新的Leader将会在broker0上，即 broker0 上的对应的副本将会从follower变成leader。

为了保证副本数据间的一致性，此时其它Follower需要与新的Leader进行数据同 步：

**其它Follower会先将各自的log文件中高于HW（水位线）的部分截取，然后开始从新的 Leader 同步。**

备注：Kafka中有一个准则，follower副本的LEO是不能够大于leader副本的，所 以新的follower副本就需要截断日志至leader副本的LEO处。

Broker 节点收到 Request 后会进行 ACK 确认这个 Request**，**其中 acks  有三个配置值:[-1 , 0 , 1] **☆☆（面试重点）**

**acks = 0**：表示不需要收到 leader 节点的 ACK 回复就会发送下一个 Request。高吞 吐，低一致性

这里是生产者直接发送到指定的分区，我不管你分区有没有给我一个确认，立马就开始发下一个，就是异步的一个过程

**acks = 1**：表示只需要接收到 leader 节点的 ACK 后就可以发送下一个 Request。

**acks = -1（all）**：表示需要接收到leaer节点和ISR节点的ACK后才会发送下一个Request。一致性较高

### kafka发送端3种不同的模式

### Fire-and-forget

这种**只发送消息，不关心消息是否发送成功**。

本质上也是一种异步发送的方式，消息先存 

储在缓冲区中，达到设定条件后批量发送。当然这是 kafka 吞吐量最高的一种方式，并配 

合参数 acks=0，这样生产者不需要等待服务器的响应，以网络能支持的最大速度发送消 

息。但是也是消息最不可靠的一种方式，因为对于发送失败的消息没有做任何处理。

### 参数调优

**buffer.memory 和 max.block.ms**

如果buffer.memory设置的很小，假如生产者生产的很快，但是缓冲区没有及时的发送到broker上就会RecordAccumulate很快就被写满了，就会造成阻塞，如果阻塞时间超过max.block.ms就会抛异常

**message.max.bytes 和 replica.fetch.max.bytes**

这个是消息的最大字节和副本的最大字节
