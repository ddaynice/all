## 1.2存算分离架构和存算一体架构该如何选择？（艾特尔信息/袋鼠云）

"选型的话，我一般会从三个维度来看：业务需求、资源弹性、部署复杂度。

（第一：看业务需求——数据量稳不稳定？）

如果业务数据规模比较稳定，数据量增长平缓，比如企业内部的核心报表分析，每天数据量差不多，那我会选存算一体。因为计算和存储在同一个节点上，数据本地性强，查询性能能做到极致，亚秒级响应。

但如果业务数据是爆发式增长的，比如互联网用户行为分析，数据量可能突然翻几倍，那存算一体就不太够用了。这时候我会选存算分离，因为存储和计算是解耦的，存储可以单独扩，不受计算资源限制。

（第二：看资源弹性——计算需求波动大不大？）

如果业务对弹性扩缩容要求不高，比如内部 BI 报表，每天固定时间跑批，计算负载很稳定，那存算一体部署简单，没有外部存储依赖，运维成本低。

但如果业务流量波动很大，比如双 11、大促期间查询量突然暴增，需要动态调整计算资源，那必须选存算分离。因为存算分离的 BE 是无状态的计算节点，计算资源可以弹性伸缩，云原生适配性很强。

（第三：看部署复杂度——团队运维能力）

存算一体架构简单，没有外部存储依赖，部署和维护都很轻量，适合团队规模不大、想快速上线的场景。

存算分离依赖共享存储（S3、OSS 这些），架构相对复杂一些，需要团队有一定的云原生运维能力。

（收尾总结）

所以简言之：追求性能稳定、部署简单，选存算一体；需要弹性扩缩、适配云原生，选存算分离。

## Doris/StarRocks在数据湖架构中的应用和优势是什么？（智汇创想）

（面试官：Doris 在数据湖架构里有什么用？）

"我觉得 Doris 在数据湖里的定位是湖仓一体的分析引擎。

以前数据湖和数据仓库是分开的。湖里存了海量原始数据，存储便宜，但查起来慢，基本只能跑离线批任务；仓库查询快，但要把数据从湖里抽出来做 ETL，链路长、有延迟，还存了两份数据。

Doris 的做法是数据不动，通过 Multi-Catalog 直接挂载湖上的 HDFS、S3、OSS，支持 Iceberg、Hudi、Paimon 这些表格式，底层是 Parquet、ORC 文件格式，在上面做高性能的实时分析。ACID、schema 演进、时间旅行这些能力由湖上的表格式保证。

这样做有几个好处：

**第一，没有数据迁移成本。**不用把数据从湖里搬到仓里，直接查原始数据，也不存在两份数据不一致的问题。

**第二，查询够快。**本身是 MPP 并行 + 向量化引擎，再配合谓词下推、列裁剪、分区分桶裁剪，把真正要扫的数据量压到最低。另外一个关键是 BE 上的 Data Cache——把热数据块缓存在本地磁盘，避免每次都回对象存储拉数据，重复查询的性能可以拉到秒级甚至亚秒级。这也是湖上查询能做到秒级最核心的原因，纯靠向量化不够，得靠缓存把 IO 短板补上。

**第三，ETL 链路变短了。**以前要'抽取-转换-加载'三步，现在直接在湖上做 ELT，中间环节少了。而且加工完的结果还能写回湖上的 Iceberg / Hive 表（Doris 2.1+、StarRocks 3.x 都支持），所以回流链路也是闭环的。

**第四，省钱。**湖用对象存储，成本很低；Doris 负责把计算效率拉上去，用高性能查询盘活低成本存储。

**第五，弹性好。**湖上的数据不构成节点本地状态，所以计算节点可以水平扩缩，数据量涨了加机器就行，高峰期扩容、平时缩掉。

（如果要再补一句，可以加：当然实际落地一般不会全查湖，通常是湖仓混用——高频访问、需要稳定亚秒响应的数据放内表，原始明细和冷数据留湖上，用统一 Catalog 联查。）

所以 Doris 让数据湖从'存得起但查不动'，变成了'存得起也查得快'，这就是湖仓一体的核心价值。"

## 1.4 Doris/Starrocks的FE节点的选举机制

FE 节点分两种角色：Follower 和 Observer。

（讲机制）

Doris 把 FE 的元数据存在一个嵌入式数据库 BDBJE 里。各个 Follower 启动时，会通过配置文件里的网络地址和端口信息，自动发现并加入同一个 Replication Group（复制组）。

BDBJE 内部使用类 Paxos 算法来进行 Master 选举。Paxos 能保证在分布式环境下，最多只有一个节点被选为 Master，不会出现脑裂。

（讲选举规则）

选举有个硬性条件：必须有过半数（>N/2）的 Follower 存活，选举才能进行。

比如 3 个 Follower，至少要有 2 个活着才能选主；5 个 Follower，至少要有 3 个活着。如果存活节点不过半，集群会拒绝服务，但不会选出一个错误的主，这是为了保证数据一致性。

阶段一（Prepare）：

  提议者向多数派发"我想提议，编号为 N"，节点承诺不再接受编号更小的提议

阶段二（Accept）：

  提议者收到过半数响应后，正式提交值；过半数节点接受后，这个值就"选定"了

（讲 Observer 的作用）

Observer 的好处是，它可以横向扩展来分担 FE 的读压力，比如元数据查询、SQL 解析这些，但它不影响选举逻辑，加多少个 Observer 都不会改变选举的多数派要求。

（收尾）

所以整个机制总结下来就是：Follower 通过 BDBJE 的 Paxos 算法选 Master，过半数存活才能选，Observer 只读不参选。这样既保证了高可用，又保证了元数据的一致性。

备注：

Paxos 是分布式一致性算法，由 Lamport 在 1998 年提出，解决的问题是：

多台机器如何在一部分节点宕机、网络分区、消息丢失/乱序的情况下，对同一个值达成一致，且保证不会出现两个“都是对的”的冲突结果。

**一句话理解：**通过“投票 + 过半数认可”的机制，让多数派说了算，少数派永远不可能推翻多数派已经定下的结论。

## 1.5 介绍下Doris的数据分布、数据存储

（面试官：讲讲 Doris 的数据分布和存储？）

"Doris 的数据分布是在建表时就定义好的，核心是两层切分：先分区，再分桶。

（讲分区）

分区是逻辑概念，一般按时间或范围划分，比如按天分区。它的主要作用是方便数据管理——删除历史数据时直接删分区，效率很高。

（讲分桶）

分桶是物理概念，在建表时通过 `DISTRIBUTED BY HASH` 指定分桶键。数据会按哈希算法打散到不同的桶里，每个桶就是一个 Tablet。Tablet 是 Doris 数据存储和副本管理的最小单元。

（讲副本分布） 

默认是 3 副本。

（讲层级关系）

从存储结构上看，层级是：Table → Partition → Bucket（Tablet）→ Rowset → Segment。

（讲 Tablet 数量）

Tablet 的总数有个计算公式：`BucketsNum × PartitionNum × ReplicaNum`。比如 3 个分区、每个分区 3 个桶、3 副本，总共就是 27 个 Tablet。这个数量要合理设计，太多会增加元数据管理开销，太少又发挥不了并行度。

（讲写入流程）

数据导入时，每次导入事务成功都会生成一个 Rowset，它带有一个版本号，由多个 Segment 文件组成。Rowset 采用 MVCC 机制，不同批次并发导入不会互相覆盖。后台会有合并策略，把多个小的 Rowset 合并成大的 Tablet 文件，减少查询时的文件扫描数量。

MVCC = Multi-Version Concurrency Control，多版本并发控制。

一句话：**写入时不覆盖旧数据，而是生成一个新的版本；读取时挑一个特定版本来读。**这样就实现了「读不阻塞写，写不阻塞读」。

（收尾）

所以总结下来，分区负责数据管理和裁剪，分桶负责分布式并行和负载均衡，Tablet 是最小管理单元，Rowset 的版本机制保证了高并发写入的安全性和一致性。

## StarRocks的分布式事务是如何实现的？ -需要背

（面试官：Doris 的分布式事务怎么实现的？）

"Doris 的分布式事务主要围绕原子性、一致性、读写隔离这三个目标来设计，涉及几个机制。

（讲 2PC）

首先是两阶段提交。因为一次导入可能同时写到多个 BE 节点上，Doris 用 2PC 来保证原子性。第一阶段，FE 作为协调者，让所有参与的 BE 先预提交数据，落盘但不对外可见；如果所有 BE 都返回成功，第二阶段 FE 再发正式提交指令，所有节点一起把数据变为可见。如果有任何一个节点失败，整个事务回滚。

（讲 MVCC）

其次是MVCC。导入过程中用户可能正在查询这张表，Doris 通过多版本机制来避免读写冲突。每次导入产生一个新的 Rowset 版本，查询只读已提交的版本，看不到未提交的数据。这样导入和查询可以并发执行，互不阻塞。

（讲 Raft）

然后是多副本一致性。一个 Tablet 有 3 个副本，Doris 用 Raft 协议来管理。写操作先写到 Leader，Leader 再同步给 Follower，必须过半数副本写成功，事务才算提交成功。这样即使某个 BE 挂了，副本之间也不会出现数据不一致。

（讲故障恢复）

最后是故障恢复。每个事务的状态都会记录在事务日志里。如果导入过程中 FE 或 BE 挂了，重启后系统会根据日志判断：已经 commit 的就继续完成，还在 prepare 状态的就回滚，保证数据一致性不受影响。

（收尾）

所以总结下来，2PC 保证跨节点的原子性，MVCC 保证读写隔离，Raft 保证多副本一致性，事务日志保证故障可恢复。这几个机制配合起来，构成了 Doris 的分布式事务能力

## Doris/Starrocks如何的FE/BE是如何保证数据一致性的？（飞轮科技

"Doris 的数据一致性是分三层来保证的，分别对应元数据层、数据副本层和全局巡检层。

（讲 FE）

首先是 FE 的元数据一致性。FE 采用类 Raft 的 BDBJE 协议，所有 Follower 组成一个复制组。元数据的写入只能由 Leader 执行，写完后必须同步到多数 Follower 并得到确认，才算提交成功。这样保证了元数据的强一致性，不会出现多个 FE 元数据不一致的情况。所有的导入、更新、删除操作都以事务为单位，要么全部成功对外可见，要么全部失败回滚，没有中间状态。

（讲 BE）

然后是 BE 的数据副本一致性。每个 Tablet 有多个副本，分布在不同 BE 节点上。BE 之间通过 Raft 日志同步，写入时采用 Quorum 多数派机制——比如 3 副本的场景，至少要有 2 个副本写入成功，才会返回给客户端成功。这样即使某个 BE 挂了，已经写入成功的多数副本数据是一致的。

另外，BE 写入时采用 WAL 预写日志 + 批量提交。数据先写日志再落盘，如果机器宕机重启，可以通过 WAL 恢复未落盘的数据，保证单节点写入不丢、不乱。

（讲 FE 巡检）

最后是 全局一致性保障。FE 会定期检查 BE 的副本状态、数据版本和分片完整性。如果发现某个副本缺失，或者版本落后于其他副本，会自动发起副本补齐和版本同步，确保全局数据最终一致。

（收尾）

所以总结下来，FE 用 Raft 保证元数据强一致，BE 用 Raft + Quorum + WAL 保证副本一致和单节点可靠，FE 定期巡检自动修复异常，三层机制共同保证了 Doris 的数据一致性。

### 注意：

## 2.2 Doris / StarRocks 为什么会查询这么快？（

（面试官：Doris 为什么查询这么快？）

"Doris 查询快不是某一个单点优化，而是从存储到执行到调度做了全链路的优化，核心思路是减少无效数据、最大化硬件利用率。我可以从五个层面来说。

（第一层：MPP 并行）

首先是架构层面的 MPP 并行。Doris 会把一条 SQL 拆成多个执行片段，分发到各个 BE 节点上并发执行。每个节点只算自己本地的数据分片，最后汇总结果。相当于把一个大任务拆成多个小任务并行算，线性扩展能力很强。

（第二层：存储层优化）

第二是存储层的数据裁剪。Doris 采用列式存储，查询时只读取需要的列，其他列完全不扫描。同时支持谓词下推，过滤条件直接在存储层生效，不满足条件的行不会传到上层。再加上 Zone Map、Bloom Filter、MinMax 这些索引，存储文件里记录了列值范围，可以直接跳过不相关的数据块，大幅减少磁盘 IO。

（第三层：向量化执行）

第三是执行层的向量化引擎。传统数据库是火山模型，一行一行处理，每行都要走一遍函数调用链。Doris 采用向量化执行，一次处理一批数据，配合 SIMD 指令并行计算，CPU Cache 命中率也更高。从'一行一算'变成'一批一算'，CPU 利用率提升非常明显。

（第四层：Pipeline 调度）

第四是Pipeline 执行模型。新版本的 Doris 引入了 Pipeline，从传统的 Pull 模式变成 Push 模式。数据准备好后主动推给下游算子，不同算子可以异步并发执行。一个算子等 IO 的时候，CPU 可以切去执行其他算子，减少了线程切换和等待，更好利用多核资源。

（第五层：查询优化器）

第五是优化器层面的 CBO 和 RBO。RBO 负责按规则做基础优化，比如列裁剪、谓词下推。CBO 会根据数据统计信息，自动选择代价最低的执行计划，比如判断 Join 时是用 Broadcast 还是 Shuffle，避免走弯路。

## ClickHouse的Join性能为什么比starrocks/doris差？

"ClickHouse 和 Doris 在 Join 性能上的差距，我觉得主要是架构设计、Join 策略丰富度、优化器和内存处理这四个层面的区别。

（讲架构）

首先是架构层面。ClickHouse 采用的是两层汇聚的执行框架，各个节点先本地计算，再把结果汇聚到单个节点做最终处理。这种架构在简单聚合场景下很快，但在复杂的多表 Join 场景下，中间结果集可能非常大，单节点汇聚很容易成为瓶颈。

Doris 和 StarRocks 是完整的 MPP 架构，查询计划被拆成多个 Fragment，在多个 BE 节点上分布式并行执行，包括 Join 和聚合都可以分布式完成，没有单点瓶颈。

（讲 Join 类型）

第二是Join 类型的支持。ClickHouse 主要支持 Global Join 和 Local Join。Global Join 本质上就是 Broadcast Join，把右表广播到所有节点。如果右表很小，这没问题；但如果两张都是大表，ClickHouse 只能硬广播，网络开销巨大。

（讲优化器）

第三是优化器。ClickHouse 缺乏基于代价的 CBO，Join 时不会根据表大小、数据分布来自动选择执行策略，基本靠默认行为或者用户手动干预。

Doris 有比较完善的 CBO，会利用统计信息判断是走 Broadcast 还是 Shuffle，自动选择代价最低的方案，避免走弯路。

（讲内存）

第四是内存处理能力。ClickHouse 的 Join 默认依赖 Hash Join，要求右表完整加载到内存。右表一旦过大，内存放不下就会溢写到磁盘，性能断崖式下降。

Doris 在设计上考虑了更复杂的 OLAP 场景，通过分区分桶裁剪、索引过滤，在 Join 前就减少数据量；Shuffle Join 可以把大表拆成分片并行处理，不依赖单节点内存。

## 1.2 Doris/StarRocks 的分区和分桶有什么区别，怎么去选择？必看，极其高频面试题

"Doris 的分区和分桶是两个不同层级的数据划分策略。

（讲区别）

分区是逻辑划分，基于业务逻辑字段，比如时间、地域。它的作用是快速定位数据区间，查询时带分区条件可以直接裁剪掉不满足的分区，减少全局扫描量。

分桶是物理划分，基于高基数字段比如用户 ID、订单 ID，通过哈希算法把数据打散。分桶的结果是 Tablet，它是 Doris 数据存储和副本管理的最小单元。分桶的作用是让数据在分区内均匀分散到各个 BE 节点，提升并行查询效率。

简单说，分区是'切蛋糕'，分桶是'分盘子'。分区先按业务维度切大块，分桶再把每块均匀分到各个节点上。

分区解决的是'查哪里'的问题，分桶解决的是'怎么均匀分布和并行计算'的问题。两者结合，才能在大数据量下既保证查询裁剪效率，又保证分布式并行性能。

（讲选择）

在使用，如果数据量大，且查询时几乎必带时间或地域等范围条件，比如日志查询、时序数据，优先选分区，利用分区裁剪减少扫描量。

如果数据量大，需要高并发多维度查询，Join 操作频繁，比如用户行为分析、订单分析，优先选好分桶键。分桶能让相同 Key 的数据落在同一个 Tablet，Join 时减少数据 Shuffle，提升性能。

实际项目中，大表通常是分区加分桶结合使用。比如用户日志表，先按天分区，再在每个分区内按 user_id 哈希分桶。这样查询带时间条件时走分区裁剪，带用户条件时走分桶定位，Join 用户维度表时还能利用 Colocation Join 本地计算。

## Bitmap 索引与Bloom filter 索引适用场景与限制（

"Bitmap 和 Bloom Filter 都是 Doris 里用于加速查询的索引，但原理和适用场景完全不同。

（讲 Bitmap）

Bitmap 索引的本质是为列的每个不同值建一个位图。比如性别列，值为'男'的行对应位图里标 1，'女'的行标 1。查询时通过位图的 AND、OR 运算快速定位满足条件的行。

它适合低基数的列，比如性别、状态码、省份，distinct 值一般不超过 1000。因为这些场景下位图数量少，存储可控，而且多条件组合查询时位运算非常快。

但它有两个明显限制：一是不适合高基数字段，比如用户 ID 有上亿个不同值，位图数量会爆炸，存储和维护成本极高；二是不适合频繁更新场景，因为单条记录更新可能要修改多个位图，写入性能损耗大。

（讲 Bloom Filter）

Bloom Filter 索引是基于哈希函数的位数组，用来快速判断'某个值是否可能存在'。它适合高基数的列，比如订单号、URL、用户 ID，这些字段 distinct 值很多，不适合建 Bitmap。

Bloom Filter 的特点是可能存在假阳性——它说'可能存在'有可能是误判，但说'肯定不存在'一定是准确的。所以它通常作为前置过滤使用：查询时先用 Bloom Filter 快速排除掉不可能满足条件的文件或数据块，减少无效扫描，然后再对剩下的数据做精确验证。

（讲限制对比）

Bloom Filter 的限制也很明显：一是有假阳性，不能用于需要精确结果的查询；二是不支持范围查询和排序，因为它只判断"等值是否存在"；三是低基数字段用 Bloom Filter 性价比低，这种场景 Bitmap 更合适。

（收尾）

所以选型上，低基数 + 等值查询 + 多条件组合 用 Bitmap；高基数 + 等值查询 + 前置过滤 用 Bloom Filter。两者也可以结合使用，先用 Bloom Filter 排除大部分数据，再用 Bitmap 精确计算剩余部分。

## 但是我们也用bitmap算uv

"这里要区分 Bitmap 索引和 Bitmap 数据类型。材料里说的 Bitmap 索引不适合高基数，是因为索引需要为每个不同值维护一个位图文件，用户 ID 有上亿个的话，位图文件数量会爆炸。

但算 UV 用的是 Bitmap 数据类型，它是把用户 ID 通过全局字典映射成连续整数，然后在一个位图里用每一位代表一个用户。1 亿用户也就 12.5MB，完全可控。查询时对位图做 OR 运算再数 1 的个数，比传统的 Hash 去重快得多。

所以 Doris 里 Bitmap 索引和 Bitmap 聚合是两套机制，不能混为一谈。"

"Doris 的列存设计围绕 OLAP 分析场景做了全链路优化，我分设计要点和与行存的对比来说。

（讲列存设计）

首先是物理布局。Doris 采用列式存储，同一列的数据在物理上连续存放。数据以 Page 为最小编码和压缩单元，多个 Page 组成一个 Segment 文件。Segment 文件尾部存储元数据和各种索引。读取时，客户端按需加载需要的列和 Page，不需要的列完全不扫描。

第二是编码与压缩。因为同一列数据类型相同，Doris 支持多种编码方式：字典编码适合重复值多的列，Delta 编码适合数值列，Run-Length 编码适合连续重复值。再配合 LZ4、ZSTD 等压缩算法，整体压缩比非常高，能大幅减少磁盘 IO。

第三是内置索引。除了常见的 ZoneMap、Short-Key、前缀索引，Doris 还支持 Bitmap、Bloom Filter 等索引。这些索引存储在文件尾部，查询时先读索引快速判断哪些 Page 或文件可以跳过，大幅减少无效扫描。

第四是写入路径。Doris 写入时数据先进入内存中的 MemTable，MemTable 满了之后批量 Flush 成列式 Segment 文件，同时生成索引。这种批量转换的方式比逐行写入列存效率高很多。后台还有 Compaction 机制，把多个小文件合并成大文件，减少查询时的文件扫描数量。

（讲与行存的对比）

列存和行存的区别，我觉得可以从五个维度来看：

第一，访问模式。 列存适合宽表的分析型负载，比如聚合、扫描、只选少数几列的场景，优势巨大。行存适合点查、事务、单行读写多的 OLTP 场景，因为一行数据存在一起，点查时一次 IO 就能读完整行。

第二，IO 与压缩。 列存同类型数据连续存放，压缩率远高于行存，磁盘带宽利用率高。但如果查询 `SELECT *` 或者需要很多列，列存要对每列做独立 IO，反而不如行存一次读一行高效。行存压缩较差，但单行读写只需一次 IO，在小表或点查场景更优。

第三，CPU 与执行模式。 列存天然适合向量化处理，配合谓词下推和早期投影（列裁剪），CPU Cache 命中率高，SIMD 指令能并行处理一批数据。行存是逐行处理，适合事务语义和复杂的行内操作。

第四，更新与写入延迟。 列存的写入通常是批量模式，数据先写 MemTable 再 Flush，随机写或频繁行级更新的代价很高，因为可能要重写整个 Segment。行存支持原地更新，延迟低，适合高并发写和更新场景。

第五，索引与跳过扫描。 列存高度依赖 ZoneMap、Short-Key、Bloom Filter、Bitmap 等索引来减少扫描量，这是列存能做高效点查和过滤的关键手段。行存通常依赖 B+ 树等主键索引做精确查找。

（收尾）

所以总结下来，Doris 的列存通过物理布局、编码压缩、内置索引和批量写入路径，专门为 OLAP 的高吞吐分析查询优化。和行存相比，它不是万能的，但在宽表聚合、少列扫描的分析场景下，性能优势非常明显。

## Doris的unique 表是如何实现合并的

Doris 的 Unique 表底层采用类 LSM-Tree 的存储结构。就是追加写而不是原地更新。

数据在写入的时候，不直接修改已有文件，而是以追加方式生成新的版本文件。

比如更新一条主键为 100 的记录，Doris 不会去找原来那条记录修改，而是直接写一个新的版本文件，里面包含主键 100 的最新数据。这样写入性能很高，因为全是顺序追加，没有随机 IO。

但追加写会带来一个问题：同一个主键可能有多个版本散落在不同文件里。

所以 Doris 依赖后台的 Compaction 机制来合并。

Compaction 会把同一个 Tablet 下的多个小文件读出来，按主键进行合并，相同主键只保留最新版本，旧版本清理掉。合并后生成一个大的文件，删除原来的小文件。

那这样就是说，一是保证主键唯一性；二是减少文件数量，提升查询效率；三是回收存储空间。

Unique 表有MOW（ Merge-on-Write）和MOR（Merge-on-Read）两种模式

MOR 是传统的 LSM-Tree 模式，写入时只追加不合并，读取时才去重合并。写入快，但查询时要现场合并多个版本，性能差。

MOW 是 Doris 优化的模式，写入时就进行合并。写入时会检查主键是否已存在，如果存在就更新，保证写入后的数据已经是去重的。这样查询时不需要再合并，性能更好，但写入代价更高。

##  doris复合索引的字段顺序影响索引效果吗？（跨越速运）

影响非常大

doris复合索引 其实就是前缀索引，自动取 Sort Key 的前 36 字节（遇到varchar还会截断的）作为前缀索引

每隔 1024 行记录一个索引条目

储存这段数据的最小值和最大值，查询的时候如果条件不在这个范围就直接跳过1024行，减少扫描量

顺序影响主要来自

第一，最左前缀匹配。前缀索引只对从最左列开始连续命中的查询有效。如果排序键是 `(A, B, C)`，查询 `WHERE B = 2` 是用不上前缀索引的，因为跳过了 A；`WHERE A = 1 AND C = 3` 也用不上，因为中间跳了 B 不连续。

第二，36 字节限制。Doris 只取 Sort Key 的前 36 字节作为前缀索引。如果前面的列太长，把额度占满了，后面的列就进不了索引。

第三，VARCHAR 截断。拼接前缀索引时，遇到 VARCHAR 列会立即截断，后续列不再进入索引。这是最容易踩的坑。

所以应该将高频过滤列、固定⻓度类型的列放在 Sort Key 的最前面，VARCHAR 列尽量靠后。

比如一个用户行为表，查询基本都是 `WHERE dt = 'xxx' AND user_id = 'xxx'`，那排序键应该设成 `(dt, user_id, ...)`。dt 是 DATE 类型占 4 字节，user_id 是 BIGINT 占 8 字节，加起来 12 字节，远小于 36 字节，两列都能进入前缀索引。如果反过来把 VARCHAR 类型的设备号放第一位，前缀索引可能直接被截断，dt 和 user_id 都进不来了。

## doris  unique 表模型的MOW 和MOR的区别和优化点（流利说/稳健医疗/极兔速递/金碧AI研究院）

这个上面说过

首先说区别

MOW 和 MOR，核心差异是合并时机。

讲核心区别）

MOW（Merge-on-Write） 是在写入时完成合并。写入过程中，Doris 会先通过主键索引查找旧行，在 delete bitmap 中标记旧行为已删除，然后写入新行。查询时直接读取，不需要再合并，所以查询性能很高，接近 Duplicate 表。

MOR（Merge-on-Read） 是在查询时才合并。写入时只追加不合并，保留每个 Key 的所有版本。查询时需要实时合并多版本，返回最新值，所以查询性能比 MOW 慢 3 到 10 倍。

（讲性能 trade-off）

MOW 用写入性能换查询性能。小批量写入时性能约低 10-20%，大批量写入时约低 30-50%，因为写入时要查主键、标记删除、维护 delete bitmap。MOR 写入快，但查询时要现场合并，CPU 和内存消耗大。

（讲 MOW 工作原理）

MOW 每次 upsert 经历 5 个阶段：

先把数据收集到 MemTable 按 Key 排序；

然后通过主键索引定位已有行；

在 delete bitmap 中标记旧行删除；

如果有 sequence_col 就按 Sequence 值仲裁保留最新的；

最后发布新 rowset。查询时通过 delete bitmap 过滤旧行，读到的就是去重后的数据。

（讲 MOW 额外优势）

MOW 还额外支持几个重要特性：

一是部分列更新，可以只更新某些字段，MOR 不支持；

二是 Filter 下推到存储层，查询过滤更高效；

三是 count(*) 查询比 Aggregate 模型快 10 倍以上；

四是读时不需要版本合并。

（讲选型）

选型上，绝大多数场景推荐 MOW，特别是实时更新、CDC 同步、维度表、报表查询这些场景。Doris 从 2.1 起也把 MOW 作为 Unique 表的默认模式。MOR 仅在写入远多于读取、且要最小化写入开销时才考虑，但官方已经标注'不再推荐'。

（收尾）

所以总结下来，MOW 是写入时算账，查询直接读；MOR 是查询时算账，写入只管追。除非是纯写入场景，否则都建议用 MOW。

##  Doris 的自动分区和动态分区有什么区别？（上海蓝标）

 Doris 中，动态分区（Dynamic Partition）和自动分区（Auto Partition）都是简化分区维护的自动化特性，其中自动分区是动态分区的演进替代方案

（讲动态分区）

那这里动态分区的工作机制是：

后台有一个定时线程，按照配置的时间周期（比如每天、每周）提前预创建分区。它强依赖系统当前时间，分区列必须是 DATE 或 DATETIME 类型。

生命周期管理上，通过 `dynamic_partition.start` 配置保留的历史分区范围，早于这个范围的分区自动删除。另外需要配置 `dynamic_partition.end` 提前预建未来若干周期的分区，否则写入未来时间的数据会失败。

动态分区的限制比较明显：

只支持单列 Range 分区，且对历史数据回补不够灵活。比如今天要补录三个月前的数据，如果当时没预建那个分区，写入就会失败。

（讲自动分区）

自动分区的工作机制是：建表时不预建空分区，数据写入时根据数据具体的值实时、按需创建对应分区。它完全与系统时间解耦，可以处理历史数据、非连续离散时间，甚至非时间类型的分区列。

自动分区支持两种类型：

> 

> 

生命周期管理上，AUTO RANGE 原生支持 `partition.retention_count`，保留指定数量的历史分区，当前和未来的分区不受影响全量保留。未来分区也不需要预建，写入时自动生成。

（讲选型）

选型上，依赖固定时间滚动周期的实时日志、监控数据，用动态分区或自动分区的 AUTO RANGE 都可以。

但如果是离线历史数据补录、分区值离散不可预测、多租户枚举列表等场景，自动分区的 AUTO LIST 是唯一选择。比如按租户 ID 分区，租户数量不固定，用自动分区写入时自动创建，非常灵活。

所以总结下来，动态分区是'定时预建'，适合简单的时间滚动场景；

##  介绍一下Doris 自增列以及与mysql的区别（上海蓝标）

### 那你说下Doris 如何设置自增列？

如果不指定起始值，就默认起始值是1

### Doris 的自增列有什么限制？和 MySQL 有什么区别？

Doris 的自增列有几个约束条件：

第一，模型限制，只支持 Duplicate 和 Unique 模型，Aggregate 模型不支持自增列。

第二，数量限制，一张表最多只能有一个自增列。

第三，类型限制，自增列必须是 BIGINT 类型，而且不能为 NULL。

（讲与 MySQL 的区别）

最重要的是和 MySQL 的区别。MySQL 的自增列由数据库严格管理，即使用户显式指定了值，MySQL 也会保证唯一性。

但 Doris 不一样：如果用户显式写入一个非 NULL 值，Doris 会保留这个值，但不会校验它是否唯一。这可能导致自增列出现重复数据，破坏唯一性约束。

只有在不写该列或写入 NULL 时，Doris 才会自动生成表级别唯一的递增值。

（收尾）

所以在 Doris 中使用自增列时要注意：如果业务强依赖自增列的唯一性，最好不要让用户端显式指定值，或者在上游做好去重。这个设计和 MySQL 的差异比较大，迁移时要特别注意。

"Doris 的自增 ID 不一定绝对连续，也不保证时间先后顺序。

（讲不连续的原因）

核心原因是 Doris 采用了分布式预分配机制。为了提升写入性能，每个 BE 节点会预先向 FE 申请一段独立的、互不重叠的 ID 区间。比如 BE1 拿到 1-10000，BE2 拿到 10001-20000。各 BE 在自己的区间内独立分配，不需要互相协调。

这样虽然写入性能很高，但会导致空洞（Gap）。比如 BE1 只用了 1-500，剩下的 501-10000 被预留了但没分配出去，最终数据里 ID 可能从 500 直接跳到 10001。

（讲不保证时间顺序）

另外，自增值的大小不能用来推断写入的先后顺序。因为不同 BE 是并行写入的，后写入的数据可能落在高 ID 区间，而先写入的数据落在低 ID 区间。比如数据 A 先写入 BE1 拿到 ID=100，数据 B 后写入 BE2 拿到 ID=50001，B 的 ID 反而更大。

（收尾）

所以如果业务需要严格连续的自增 ID，或者用自增 ID 来推断时间顺序，Doris 的自增列不适合。这种场景下，建议用显式的时间戳字段来记录顺序，而不是依赖自增 ID。

##  Doris和starrocks 如何实现数据更新？

（面试官：Doris/StarRocks 怎么实现数据更新？）

"Doris 和 StarRocks 的数据更都是不直接修改磁盘数据，而是追加写入新版本 + 逻辑覆盖 + 后台合并。

（讲统一机制）

这俩更新或删除时，系统会写入一条新记录，或者写入一个删除标记（Delete Bitmap）。

查询时通过版本号和删除标记合并出最新结果。

这里旧数据不会立即删除，而是由后台的 Compaction 任务定期清理，然后释放空间。

这种设计的好处是写入性能极高，因为全是顺序追加，没有随机 IO。

（讲 Doris 的模型差异）

在 Doris 中，不同表模型的更新能力不一样：

对于 UPDATE 和 DELETE 操作，Doris 的实现方式是：扫描满足条件的行，然后写回新行或写入删除标记。查询时过滤掉带删除标记的行，物理回收由后台 Compaction 完成。

（讲 StarRocks 的差异）

StarRocks 主推 Primary Key 表，设计上更适合高频更新。

它通过主键索引加 DelVector（删除向量）来实现更新。

Update 操作本质上是 Delete 加 Insert：标记旧行删除，写入新行，并更新主键索引指向最新数据。查询时直接读取最新记录，不需要在线合并，所以查询性能很高，特别适合 CDC 实时同步事务型数据。

StarRocks 历史上还有 Unique/Update 表，通过版本号语义实现多版本取最新，但目前正在逐步被 Primary Key 表替代。

（收尾）

所以总结下来，两者的更新都是基于 LSM-Tree 的追加写思想，Doris 通过 Unique 模型的 MoW 策略实现高效更新，StarRocks 通过 Primary Key 表的主键索引和删除向量进一步优化了更新和查询性能。

## Doris/Starrocks如何保证导入的事务及原子性？（北京花径教育科技）

两个方面吧

导入原子性和Label去重

doris的所有导入操作都有原子性保证，一个导入作业中的数据要么全部成功，要么全部失败，不会出现部分数据导入成功的情况。

是通过两段提交实现的，FE作为协调者，让所有参与的BE先预提交，都成功之后再正式提交。

如果又任何一个节点失败，整个十五回滚，已经写入的数据对外不可见。

Label 每个导入作业都可以设置一个label，他是用户自定义的，具有业务逻辑属性的字符串

用来唯一标识一个导入任务

Label 的核心作用是保证相同 Label 只会成功导入一次。如果我用 Label `order_20240101_001` 导入一次成功了，再次用同样的 Label 导入时，Doris 会拒绝，返回 Label 已存在，防止重复写入。但如果上次导入失败了，相同 Label 是可以重试的。

这个 Label 机制配合上游的 At-Least-Once 语义，可以实现 Exactly-Once。比如 Flink CDC 同步到 Doris，Flink 保证数据至少投递一次，可能因网络抖动重复发送。Doris 用相同的 Label 接收，重复的请求会被拒绝，最终数据只写入一次，实现端到端的精确一次。
