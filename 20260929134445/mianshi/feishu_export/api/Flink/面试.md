## 什么是Flink？（必背）

Flink 是一个开源的分布式计算框架，Apache 顶级项目，最大的特点是流批一体——用同一套模型既能做实时流处理，也能做批量处理。流批一体么

我觉得它最核心的设计有三个：

第一，事件时间机制。 Flink 算窗口的时候，用的是数据自己携带的时间戳，而不是数据到达系统的时刻。这样即使数据因为网络抖动乱序到达，算出来的结果依然是准确的，这对我们做的实时监控、预警这类场景特别关键。

第二，Exactly-Once 语义。 通过 Checkpoint 机制，任务挂了重启之后，每条数据只被处理一次，中间状态也不会丢。这一点是 Flink 区别于 Storm 这类早期框架的核心竞争力——做有状态的累计计算，比如用户实时画像、实时 GMV 统计，没有这个根本不敢上生产。

第三，生态和易用性。 原生对接 Kafka、MySQL、ES、HDFS 这些常用存储，还有 SQL 和 Table API，业务方很多需求用 SQL 就能提，不用都写 DataStream。

总结一句：Flink = 流批一体 + 低延迟高吞吐 + 精确一次语义，这也是它在实时领域成为事实标准的原因。"

问题：什么是checkpoint机制

Checkpoint = 把"算到哪"和"消费到哪"拍进同一张照片，挂了就从照片恢复，重算的数据会被回滚抵消，所以结果不重不漏。

Checkpoint 是 Flink 的故障恢复机制，作用是定期给任务的全量状态拍快照，让任务挂了之后能恢复到崩溃前的那一刻，保证数据不重不漏。

它的工作流程是这样的：

JobManager 会定期往数据流里插入一个特殊标记，叫 Barrier。Barrier 跟着数据一起流动，每个算子收到 Barrier 之后，就把自己当前的状态异步地快照到持久化存储，比如 HDFS。所有算子都快照完成并汇报给 JobManager，这次 Checkpoint 才算成功。

这里有个关键点：如果一个算子有多路输入，比如双流 Join，它要等所有输入通道的 Barrier 都到齐才开始快照，这个过程叫 Barrier 对齐。对齐保证了快照刚好切在两条流同一个逻辑位置，这是实现 Exactly-once 的基础。

挂了之后的恢复过程：Flink 加载最近一次成功的快照，把所有算子状态恢复回去，同时 Kafka Source 会根据快照里记录的 offset 重新消费。这样虽然部分数据物理上会重算，但因为状态先回滚了，最终效果和每条数据只处理一次完全一样，这就是 Exactly-once 语义。

在生产上我一般还会关注两个点：一是状态大的时候用 RocksDB 做状态后端，配合增量 Checkpoint，避免每次全量快照太伤性能；二是反压严重时 Barrier 排队导致 Checkpoint 超时，可以开非对齐 Checkpoint 来缓解。

##  Flink 相⽐ SparkStreaming 有什么区别（了解）

"这两个框架的区别，我觉得可以先用一句话概括：Spark Streaming 是微批处理，Flink 是真正的流式处理。Spark Streaming 是把源源不断的数据切成一小批一小批，用批引擎去算；Flink 是逐条处理，来一条算一条。

第一，时间语义。 Spark Streaming 只支持处理时间，也就是数据到达系统的时间。Flink 支持处理时间、事件时间、摄入时间三种，还有 Watermark 机制处理乱序。业务上如果要做"统计每个自然分钟的订单量"，用事件时间算出来的才是真实业务时间的结果，这一点 Spark Streaming 做不到。

**这里比如有一笔订单 用户下单的时间是12:00:59 但是因为网络传输，日志采集延迟等这个数据过了20秒才到达。系统的时间是12:01:19了**

**现在程序要给它开窗，问题来了——按哪个时间开窗？**

**按处理时间（Spark Streaming 的方式）：**

**程序只看"数据到达时系统几点"，于是把这条 12:00:59 的订单算进了 12:01 这一分钟。**

**对业务来说，如果运营在 想看"12:00 这一分钟成交了多少单"，看到的数字是偏低的，而且这个错误永远不会被修正，因为窗口已经按错误的对齐方式算完了。**

**按事件时间（Flink 的方式）：**

**程序看的是订单自己携带的 12:00:59，于是把它正确地归入 12:00 这一分钟的窗口，等 Watermark 推进到 12:01:00 之后才触发这个窗口的计算。**

第二，容错和一致性。 Spark Streaming 的 Checkpoint 只能保证数据不丢，重启后可能重复消费，想做到 Exactly-Once 得自己在上层兜底，比如靠幂等写入。Flink 是框架层面内置了 Exactly-Once——Checkpoint 快照状态

第三，调度和资源模型。 Spark 那边是 Master/Worker/Driver/Executor；

Flink 是 JobManager 负责任务调度和 Checkpoint 协调，TaskManager 提供 Slot 跑任务。

Flink 提交作业时会经历 StreamGraph → JobGraph → ExecutionGraph 的转换，ExecutionGraph 是它调度的核心数据结构。

第四，状态管理。 Flink 有一等公民的状态机制，Keyed State、Operator State、State Backend，做大规模有状态计算是原生能力；Spark Streaming 的 state 能力相对弱一些。

总结：延迟要求毫秒级、需要事件时间、需要精确一次，选 Flink；如果是分钟级的准实时、团队技术栈统一在 Spark 上，Spark Streaming 也能用，但新项目的实时场景业界基本都转向 Flink 了。"

## Flink 运⾏时的架构组件有哪些？各⾃有什么作⽤？（理解背诵）

### 首先是组件有那些？

四个：

作业管理器（ JobManager ）、资源管理器 （ ResourceManager ）、任务管理器（ TaskManager ），以及分发器（ Dispatcher ）

作业管理器-Jobmanager

Jobmanager进程又有三个组件：ResourceManager 、 Dispatcher 和 JobMaster

首先是TaskManager 这个是真正干活的worker进程，每个TaskManager 有若干个Slot，slot是Flink里最小的资源调度单元，任务最终都是跑在slot上的。

然后还需要一个大脑来指挥，就是作业管理器（ JobManager ），客户端提交的作业先变成JobGraph,

然后JobManager 把JobGraph展开成 ExecutionGraph——也就是物理执行图，然后它向 ResourceManager 申请 Slot，拿到资源后把任务分发到各个 TaskManager 上。

作业运行期间，所有的中央协调都在 JobManager 这边：任务调度、Checkpoint 的触发和协调、失败恢复，这些都是业管理器来处理。

还有分发器（ Dispatcher ）它对外提供 REST 接口接收作业提交，每来一个作业就启动一个对应的 JobMaster；我们平时看的 Flink Web UI 其实也是 Dispatcher 启动的。

整体来说就是

Dispatcher 接收，ResourceManager 管资源，JobMaster 管作业执行，TaskManager 干活。 整个集群中 ResourceManager 只有一个，JobMaster 是每个作业一个。"

### 总述

Flink 运行时架构主要有四个核心组件：Dispatcher（分发器）、ResourceManager（资源管理器）、JobManager（作业管理器，核心是 JobMaster）和 TaskManager（任务管理器）。因为 Flink 是 Java 和 Scala 写的，所以这些组件都跑在 JVM 上。

【Dispatcher —— 入口】

你像Dispatcher 是集群的入口，它提供了一个 REST 接口，我们提交作业就是通过它提交的。它收到请求后，会为每个作业启动一个 JobMaster。另外，Flink Web UI 严格来说也是由 Dispatcher 启动的，用来展示和监控作业的执行情况。

【ResourceManager —— 管资源】

ResourceManager 负责 slot（任务槽）的分配、提供和回收。当 JobMaster 申请资源时，ResourceManager 会把有空闲 slot 的 TaskManager 分配给它。如果现有 slot 不够，它还可以向资源提供平台（比如 YARN、K8s）发请求，动态启动新的 TaskManager 容器；空闲的 TaskManager 它也会负责释放掉，避免资源浪费。

#### 这里有两个常被追问的点，可以主动补充：

整个 Flink 集群只有一个 ResourceManager，实现 HA 时可以多个进程 standby，通过 ZooKeeper 做 leader 选举；

它和 YARN 的 ResourceManager 不是一回事——Flink 的 ResourceManager 只管 Flink 自己的 slot 资源，YARN 的 ResourceManager 管的是整个集群的容器资源。

【JobMaster —— 管单个作业】

JobMaster 负责管理单个 JobGraph 的执行。提交上来的是一个逻辑数据流图 JobGraph（以及打包好的 JAR 包），JobMaster 会把它转换成物理执行图 ExecutionGraph——也就是所有可以并发执行的任务的图，然后拿去运行。

它还负责：

调度各个 Task 到 TaskManager 的 slot 上；

通过 Checkpoint Coordinator 协调整个作业的 Checkpoint（触发开始和确认完成）；

与 TaskManager 保持通信；

故障恢复时，从 Recovery Metadata 里读取元数据恢复作业。

要注意的是：一个集群可以同时跑多个作业，每个作业都有自己的 JobMaster；而 JobManager 整体就是由 ResourceManager、Dispatcher、JobMaster 这三个部分组成的。

【TaskManager —— 干活的】

TaskManager 是真正执行任务的进程。每个 TaskManager 内部有若干个 slot，slot 是 Flink 中定义的处理资源单元，slot 的数量决定了它能同时跑多少个 task。启动后 TaskManager 会先向 ResourceManager 注册自己的 slot，收到指令后就把 slot 提供给 JobMaster 调度。运行过程中，同一个作业的多个 TaskManager 之间还可以互相交换数据。

它内部的主要组件有：

Memory & I/O Manager：内存和 I/O 管理；

Network Manager：网络缓冲管理；

Actor System：负责组件间的网络通信。

【一句话收尾】

所以整个流程可以串成一句话：Dispatcher 收作业、起 JobMaster → JobMaster 把 JobGraph 转成 ExecutionGraph 并申请资源 → ResourceManager 分配 slot → TaskManager 领任务真正执行。

### 追问：

#### JobGraph 和 ExecutionGraph 的区别？

JobGraph 是逻辑图（算子级、未并行化），ExecutionGraph 是物理图（按并行度展开成 task，可直接调度执行）

#### slot 是什么？slot 数怎么定？

slot 是 TaskManager 内的独立资源单元，一般按 CPU 核数设置；slot 只隔离内存，CPU 默认共享

#### 作业提交流程？

Dispatcher 收作业、起 JobMaster → JobMaster 把 JobGraph 转成 ExecutionGraph 并申请资源 → ResourceManager 分配 slot → TaskManager 领任务真正执行

## Flink 的任务提交流程（理解背诵

### 第一层：通用提交流程（standalone 视角，必背）

作业提交时，各组件是这样协作的：

App 提交应用到 Dispatcher；

Dispatcher 启动 JobMaster（每个作业一个 JobMaster）；

JobMaster 向 ResourceManager 请求 slots；

ResourceManager 启动/调度 TaskManager（资源不够时向 YARN、K8s 等平台申请容器启动新的 TaskManager）；

TaskManager 向 ResourceManager 注册自己的 slots；

ResourceManager 发出提供 slot 的指令；

TaskManager 把 slots 提供给 JobMaster；

JobMaster 把要执行的任务提交到 slots 中执行；

运行过程中，同一个作业的各个 TaskManager 之间互相交换数据。

一句话串起来就是：Dispatcher 接收作业起动 JobMaster → JobMaster 找 ResourceManager 要 slot → TaskManager 注册并提供 slot → 任务下发到 slot 上跑起来，节点间交换数据。

### 第二层：YARN 模式提交流程（高频追问，重点准备）

如果部署在 YARN 上（per-job / application 模式），流程会多一层 YARN 的交互：

Client 先把 Flink 的 Jar 包和配置上传到 HDFS（这是后面所有节点构建环境的来源）；

Client 向 YARN 的 ResourceManager 提交任务；

ResourceManager 分配一个 Container，并通知对应节点的 NodeManager 启动 ApplicationMaster——Flink 的 JobManager 就跑在 ApplicationMaster 里面；

ApplicationMaster 启动后，从 HDFS 加载 Flink 的 Jar 包和配置构建 Flink 环境，然后启动 JobManager；

JobManager 向 YARN 的 ResourceManager 申请资源，ResourceManager 分配 Container 后，由 ApplicationMaster 通知资源所在节点的 NodeManager 去启动 TaskManager；

NodeManager 加载 HDFS 上的 Jar 包和配置构建环境，启动 TaskManager；

TaskManager 启动后向 JobManager 发送心跳，等待 JobManager 分配任务。

后面就回到了通用流程：JobMaster 申请 slot → 任务下发执行。

### Jar 包和配置上传到 HDFS 的意义

因为 TaskManager 可能分布在任意节点，每个节点从 HDFS 拉取统一的 Jar 和配置，保证环境一致。

### 部署模式不同，流程会省略

standalone 模式 TaskManager 已经常驻、提前注册好了 slot，所以第 4、5 步可以直接跳过；如果组件跑在同一个 JVM 里（比如 MiniCluster 本地测试），流程还可以更简化。

### 和上一题串起来：

本质就是上一题的组件协作——Dispatcher、JobMaster、ResourceManager、TaskManager 各司其职，YARN 只是在“启动 TaskManager 进程”这一层包了一层容器管理。

### YARN 上 ApplicationMaster 和 JobManager 什么关系？

Flink 的 JobManager 跑在 ApplicationMaster 这个容器进程里，AM 负责向 YARN 申请资源和通知 NodeManager 启动 TaskManager

### 为什么 Jar 要传 HDFS？

所有节点的 NodeManager/TaskManager 都从 HDFS 拉取统一环境，保证一致性，同时避免重复传输

### Application 模式和 Per-Job 模式区别？

 Per-Job 的 main() 在 Client 执行；Application 模式把 main() 移到集群端（ApplicationMaster）执行，减轻 Client 压力，一个应用一个 JobManager

## 任务调度原理（理解背诵）

Client 只提交（转图 → 发 JobGraph → 可断开）

JobManager 三件套（Scheduler 调任务、Checkpoint Coordinator 管 CK、Dataflow Graph 是依据）

TaskManager 干活 + 汇报（心跳 / 状态 / 统计）

节点之间流换数据

【开头总起】

Flink 的任务调度涉及三类角色：Client、JobManager 和 TaskManager，这三个都是独立的 JVM 进程。

【Client —— 只管提交，不参与运行】

首先Client 并不是运行时的一部分。

它把程序代码经过优化器 / Graph Builder 转换成数据流图（JobGraph），然后把 JobGraph 提交给 JobManager。提交之后，Client 可以断开连接，也可以保持连接等待接收计算结果——它不参与作业的实际执行。

【JobManager —— 调度中心】

JobManager 收到 JobGraph 后，内部有三个核心组件来负责调度：

Scheduler：负责把任务调度到各个 TaskManager 的 slot 上执行，可以下发 Deploy / Stop / Cancel 指令；

Checkpoint Coordinator：负责协调整个作业的 Checkpoint，向 TaskManager 触发 Checkpoint；

同时维护 Dataflow Graph（执行图），这是任务调度的依据。

【TaskManager —— 执行者】

TaskManager 是 worker 进程，内部有若干个 TaskSlot，任务就跑在 slot 里。slot 底下有三个支撑组件：Memory & I/O Manager（内存和 I/O 管理）、Network Manager（网络缓冲管理）、Actor System（通信）。

【运行期的交互关系】

运行起来之后，三者形成这样的交互闭环：

Client → JobManager：提交 JobGraph，以及取消 / 更新作业；

JobManager → TaskManager：部署任务、触发 Checkpoint；

TaskManager → JobManager：定时上报心跳、任务状态、统计信息；

TaskManager ↔ TaskManager：之间以流（Data Streams）的形式传输数据。

【一句话总结】

Client 转图提交、JobManager 调度和协调 Checkpoint、TaskManager 在 slot 里干活并汇报心跳，TaskManager 之间以流的方式交换数据——这就是 Flink 的任务调度原理。

## 如何理解 Flink 中的 Slot （必背）

【slot 是什么】

Flink 中每个 worker，也就是 TaskManager，都是一个 JVM 进程。为了控制一个 worker 能接收多少个 task，TaskManager 引入了 task slot 来进行资源管控——每个 TaskManager 至少有一个 slot。

【slot 代表什么资源】

每个 slot 代表 TaskManager 拥有资源的一个固定大小的子集。比如一个 TaskManager 有 4 个 slot，那这个 JVM 的内存就会被平均分成 4 份，每个 slot 占 25%。任务的并行度就是由 TaskManager 中 slot 的数量决定的。

【slot 和线程的关系】

一个 slot 里可以运行一个或多个线程；同一个 slot 内的线程共享同一个 JVM 的内存资源——这意味着它们之间不会为了内存而竞争。而且在同一个 JVM 进程内，这些 task 还可以共享 TCP 连接（基于多路复用）和心跳消息，也可能共享数据集和数据结构，这样就减少了每个 task 的开销。

【和 Spark 对比（原资料的点睛之笔）】

slot 类似于 Spark 中的 task，本质上就是 worker 节点上的一个线程，一般一个 slot 独占一个 core。

【最后一个关键说明】

slot 的数量由参数 taskmanager.numberOfTaskSlots 决定，slot 只对内存做了隔离，并没有对 CPU 做隔离——CPU 是各 slot 共享的。

### 追问预案

#### slot 隔离了什么？没隔离什么？      

  隔离内存（均分 JVM 内存），不隔离 CPU（CPU 共享）

#### slot 数怎么设置？        

一般等于 TaskManager 的 CPU 核数，保证一个 slot 一个 core

#### 同 slot 内的任务有什么好处？       

共享 JVM 内存、TCP 连接（多路复用）、心跳，减少开销

#### slot 数和作业并行度什么关系？      

  并行度上限受 slot 总数限制；开启 slot sharing 后，一个 slot 可容纳一个作业不同算子的子任务，slot 数可以小于总并行度

#### 和 Spark 的 executor/core 类比？       

 slot 类似 Spark 的 task，是 worker 上的一个线程；TaskManager 类似 executor

## Flink 的核⼼数据集 DataStream 的组成（理解背诵）

DataStream 程序主要由 3 部分组成：

第一部分：StreamExecutionEnvironment 初始化。 首先要创建和初始化 StreamExecutionEnvironment，它是通过 DataStream API 构建 Flink 作业的执行环境入口。在这一步可以设置各种配置信息，比如 ExecutionConfig、CheckpointConfig，还有 StateBackend（状态后端）、TimeCharacteristic（时间语义） 等变量。

第二部分：业务逻辑代码转换。 env 提供了创建 DataStream 的各种方法，比如通过 env.readTextFile() 读取文本数据构建 DataStreamSource。

DataStreamSource 是整条 DataStream 的头节点，之后所有的 DataStream 操作都以它为起点。DataStream API 提供了各种转换算子，比如 map、reduce、keyBy 等，用这些算子把完整的计算逻辑串联起来。

第三部分：程序执行 env.execute()。 调用 env.execute() 时，会基于 DataStream 之间的转换关系生成 StreamGraph，然后把 StreamGraph 转换成 JobGraph，最后将 JobGraph 提交到集群执行。

一句话总结：先建环境、再写转换逻辑、最后 execute 提交——execute 是触发点，前面两步只是构建逻辑，真正生成图并提交是在 execute 里发生的。

## Flink 中是否也有 Spark 中的宽窄依赖的概念（了解）

有的，Flink 中算子之间传输数据有两种形式：one-to-one（forwarding） 和 redistributing，具体是哪一种取决于算子的种类。它们正好可以类比 Spark 的窄依赖和宽依赖。

第一种：one-to-one（对应 Spark 的窄依赖）。 流在传输时维护着分区以及元素的顺序，比如 source 和 map 之间——map 算子的子任务看到的元素个数和顺序跟 source 算子的子任务完全一样。像 map、flatMap、filter 这些算子都是 one-to-one 的对应关系。对于并行度一样的 one-to-one 操作，每个子任务可以合并产生一个子任务——这就是 Flink 的算子链（Operator Chain）。

第二种：redistributing（对应 Spark 的宽依赖）。 流的分区会发生改变，每一个算子的子任务会依据所选择的 transformation 把数据发送到不同的目标任务。比如 keyBy() 会基于 hashCode 重新分区，broadcast 和 rebalance 会重新分区，这些算子都会引起 redistribute 过程——这个 redistribute 就类似于 Spark 中的 shuffle 过程。

一句话总结：map/filter/flatMap 这类保序不换分区的算子是窄依赖，可以串成算子链；keyBy/broadcast/rebalance 这类换分区的算子是宽依赖，等价于 Spark 的 shuffle，是物理隔断点。

### 追问预案

#### 哪些算子是窄依赖？        

map、flatMap、filter 等，分区和元素顺序不变

#### 哪些算子是宽依赖？        

keyBy（hashCode 重分区）、broadcast、rebalance、rescale 等

#### 算子链形成的条件？        

one-to-one 且并行度相同，且没有禁用 chaining

#### 为什么要做算子链合并？        

减少线程切换、序列化和网络传输开销，本地流水线执行

#### 和 Spark shuffle 的区别？       

 思想类似但机制不同：Flink 的 redistribute 是流式传输、边算边发，Spark shuffle 需要 map 端先落盘再 reduce 端拉取

## Flink 中的四张图（了解）

Flink 作业执行过程中有四张图，是一步步转换来的：StreamGraph → JobGraph → ExecutionGraph → 物理执行图。

第一张：StreamGraph。 这是根据用户通过 DataStream API 写的代码生成的最初的 DAG 图，用来表示程序的拓扑结构。这一步一般在客户端完成。

第二张：JobGraph。 StreamGraph 经过优化后生成 JobGraph，这是提交给 JobManager 的数据结构，确定了当前作业中所有任务的划分。它最主要的优化是：将符合条件（one-to-one、并行度相同）的节点链接在一起合并成一个任务节点，形成算子链，这样可以减少数据交换的消耗。JobGraph 一般也是在客户端生成的，在作业管理器那边，JobMaster 拿到的就是 JobGraph。

第三张：ExecutionGraph。 JobMaster 收到 JobGraph 后，会根据它生成 ExecutionGraph。它是 JobGraph 的并行化版本——把每个节点的并行度展开成一个个并行的子任务——是调度层最核心的数据结构。生成位置在 JobManager 上。

第四张：物理执行图。 JobMaster 生成执行图后，会把它分发给 TaskManager，各个 TaskManager 根据执行图去部署任务，最终物理执行过程也会形成一张图，一般叫物理图（Physical Graph）。要注意，它并不是一个具体的数据结构，只是具体执行层面的概念。生成位置在 TaskManager 上。

一句话总结：StreamGraph 是代码的拓扑、JobGraph 是算子链优化后可提交的逻辑图、ExecutionGraph 是并行化后的调度图、物理图是 TaskManager 上真正跑起来的样子。

## 你知道 Flink 中的任务链吗？（了解

Flink 采用一种叫 算子链（Operator Chain） 的优化技术：把相同并行度的 one-to-one 操作相连的算子链接在一起形成一个 task，原来的每个算子就成为这个 task 里面的一部分，叫做 subtask（子任务）。

链在一起要满足两个条件：

两个或多个算子必须设置成相同的并行度；

它们之间要通过本地转发（local forward） 的方式连接——也就是 one-to-one 的数据传输。

在一个 DAG 图中，不能被 chain 在一起的 Operator 会被分隔到不同的 Task 中。一般一个 Task 占用一个 slot，也就是说 Task 是 Flink 中资源调度的最小单位。

**为什么这么做？ **

在 StreamGraph 转换成 JobGraph 的过程中，关键就是把多个 StreamNode 优化成一个 JobVertex，对应的 StreamEdge 转化成 JobEdge，JobVertex 和 JobEdge 之间通过 IntermediateDataSet（中间数据集） 形成生产者和消费者的连接关系。每个 JobVertex 就是 JobManager 的一个任务调度单位。

如果不做这个优化，相关联的几个算子会被放到不同的 Task 里，执行时就会产生数据交换——网络通信、线程切换、上下文切换，这些开销都很大。所以 Flink 在 StreamGraph 转 JobGraph 的过程中，把可以优化的算子合并为一个算子链（形成一个 Task），这样链上的算子就可以放到同一个线程中去执行，数据在本线程内直接传递，不用走网络和序列化，提高了任务执行效率。

一句话总结：算子链就是把“并行度相同 + one-to-one”的算子合并成一个 Task 放在一个线程里跑，把本来要走网络的数据交换变成线程内的本地传递，这是 Flink 流水线执行性能的关键。

## Flink 的并⾏度是什么？（理解背诵）

 在 Flink 执行过程中，每个算子（operator）可以包含一个或多个子任务（operator subtask），这些子任务分布在不同的线程、不同的物理机或不同的容器中完全独立地执行。

一个特定算子的子任务个数，就称为这个算子的并行度（parallelism）。

一般情况下，一个 Streaming 程序的并行度，可以认为就是它所有算子中最大的并行度。而且一个程序中不同的算子可以有不同的并行度。

【并行度怎么设置——四级优先级】 优先级从高到低依次是：

算子级别：在代码中单独指定某个算子的并行度，优先级最高，会覆盖后面所有的设置；

执行环境级别：如果算子没有单独设置，就用 env.setParallelism() 设置的全局并行度；

提交参数级别：代码里完全没设置，就用提交时 -p 参数指定的并行度；

配置文件级别：什么都没指定，就用配置文件里的默认并行度（parallelism.default）。

【一个特例】 并行度不是想设多大就多大，有的算子会受自身实现的影响。比如读取 socket 文本流的 socketTextStream，它本身就是非并行的 Source 算子，所以无论怎么设置，它运行时的并行度都是 1，数据流图上就只有一个并行子任务。

【生产实践】 在实际中在代码中只针对算子设置并行度，不设置全局并行度——这样方便我们提交作业时通过 -p 进行动态扩容，不用改代码重新打包。

## 任务槽和并⾏度的关系？（理解背诵）

面试口语版答案

【总述：一对“容量 vs 用量”的关系】

Slot 和并行度都跟并行执行有关，但是完全不同的概念：

task slot 是静态概念，指 TaskManager 具有的并发执行能力，由参数 taskmanager.numberOfTaskSlots 决定（一般建议设成 CPU 核心数）；

并行度是动态概念，指 TaskManager 运行时实际使用的并发能力，由 parallelism.default 等参数设置。

打个比方：slot 是酒店的房间数，并行度是你实际入住的人数。入住人数 ≤ 房间数就能住下——所以并行度小于等于可用 slot 总数时程序可以运行，slot 不一定要全部占用，十分力气可以只用八分；但如果并行度大于可用 slot 总数，超出了并行能力上限，程序就只好等待 ResourceManager 分配更多资源。

由此有个计算公式：需要的 TaskManager 数 = 算子并行度 ÷ 每个 TM 的 slot 数（向上取整）。

【用例子走一遍】

假设集群有 3 个 TaskManager，每个 3 个 slot，共 9 个 slot，最多能并行执行 9 个任务。WordCount 的算子是 source → flatMap → reduce → sink，因为所有算子并行度相同，source 和 flatMap 可以合并算子链，所以最终是 3 个任务节点。

然后分四种情况看 slot 的占用：

并行度 = 1（默认）：总共 3 个任务，由于 slot 共享，不同算子的任务可以挤在同一个 slot 里，最终只占用 1 个 slot，8 个空闲——资源严重浪费；

并行度 = 2：总共 6 个任务，共享后占用 2 个 slot，7 个空闲，资源还是没充分利用；

并行度 = 9：27 个任务，正好占满全部 9 个 slot——这是当前集群资源下能执行的最大并行度，计算资源充分利用，效率最高；

给 sink 单独设并行度 = 1：比如输出是写文件，不希望并行写多个文件，用 writeAsCsv(...).setParallelism(1)。这时其他算子并行度还是 9，总共 19 个子任务，根据 slot 共享原则依然占用全部 9 个 slot，只是 sink 只在其中 1 个 slot 上执行，其他 TaskManager 的数据全部发送到这个 sink。

第 4 种情况也印证了一个结论：整个程序的并行度，就是所有算子并行度中最大的那个，它代表了程序需要的 slot 数量。

【一句话总结】

slot 是静态的资源容量，并行度是动态的资源用量；程序需要的 slot 数等于最大算子并行度，并行度设成总 slot 数时资源利用率最高。
